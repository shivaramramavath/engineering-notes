# Route Handlers

A **Route Handler** is a `route.ts` file that answers HTTP requests for a URL using the standard Web `Request` and `Response` APIs. It is how a Next.js app exposes an API: JSON endpoints, webhooks, file downloads, feeds, OAuth callbacks, anything that is not a page.

> Verified against the Next.js 16.4 docs.

## What it is, and when to use it

| You need | Use |
|---|---|
| Your own UI changes data | [Server Actions](../07-server-actions/README.md) |
| Your own UI reads data | Server Components ([05 Data Fetching](../05-data-fetching/README.md)) |
| Something **outside** your UI must call you (webhook, mobile app, third party, cron) | **Route Handler** |
| Non-HTML output (`rss.xml`, `llms.txt`, images, CSV, streams) | **Route Handler** |
| OAuth / payment callback URL | **Route Handler** |
| A public API for other developers | **Route Handler** |

Route Handlers are **public HTTP endpoints**. Anyone who knows the URL can call them, so every one needs its own authentication, validation and error handling.

## The convention

Create `route.ts` inside `app/`. Export a function named after the HTTP method.

```ts
// app/api/hello/route.ts  →  /api/hello
export async function GET() {
  return Response.json({ message: "Hello" });
}
```

Supported methods: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`. A method you did not export returns `405 Method Not Allowed`. If you do not export `OPTIONS`, Next.js adds one and sets the `Allow` header from the methods you did export.

```ts
// app/api/posts/route.ts
export async function GET(request: Request) { /* list */ }
export async function POST(request: Request) { /* create */ }
```

### One rule: no `page.tsx` beside it

A segment can have **either** a `page` **or** a `route`, not both. Each one takes over all HTTP verbs for that URL.

| Files | Result |
|---|---|
| `app/page.tsx` + `app/route.ts` | Conflict |
| `app/page.tsx` + `app/api/route.ts` | Valid |
| `app/[user]/page.tsx` + `app/api/route.ts` | Valid |

Route Handlers do not use layouts and do not take part in client-side navigation. The `/api` prefix is a convention you choose, not a requirement.

## Dynamic segments

`params` is a **Promise**. Await it.

```ts
// app/api/posts/[id]/route.ts
import type { NextRequest } from "next/server";

export async function GET(
  _req: NextRequest,
  ctx: RouteContext<"/api/posts/[id]">,
) {
  const { id } = await ctx.params;
  const post = await getPost(id);
  if (!post) return Response.json({ error: "Not found" }, { status: 404 });
  return Response.json(post);
}
```

`RouteContext<"/api/posts/[id]">` is a globally available helper that types `params` from the route string. Its types are generated by `next dev`, `next build` or `next typegen`. Without it, annotate manually:

```ts
{ params }: { params: Promise<{ id: string }> }
```

| File | URL | `params` |
|---|---|---|
| `app/api/posts/[id]/route.ts` | `/api/posts/7` | `{ id: "7" }` |
| `app/files/[...path]/route.ts` | `/files/a/b` | `{ path: ["a", "b"] }` |

## A complete, realistic handler

```ts
// app/api/posts/route.ts
import { NextResponse, type NextRequest } from "next/server";
import { z } from "zod";
import { auth } from "@/lib/auth";
import { db } from "@/lib/db";

const CreatePost = z.object({ title: z.string().trim().min(1).max(120) });

export async function POST(request: NextRequest) {
  // 1. authenticate
  const session = await auth();
  if (!session?.user) {
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  }

  // 2. parse and validate
  let body: unknown;
  try {
    body = await request.json();
  } catch {
    return NextResponse.json({ error: "Invalid JSON" }, { status: 400 });
  }
  const parsed = CreatePost.safeParse(body);
  if (!parsed.success) {
    return NextResponse.json({ error: "Invalid input", issues: z.flattenError(parsed.error).fieldErrors }, { status: 400 });
  }

  // 3. do the work
  try {
    const post = await db.post.create({
      data: { title: parsed.data.title, authorId: session.user.id },
      select: { id: true, title: true },
    });
    return NextResponse.json(post, { status: 201 });
  } catch (err) {
    console.error("create post failed", err); // log details on the server
    return NextResponse.json({ error: "Internal error" }, { status: 500 }); // generic to the client
  }
}
```

The order is the same as for Server Actions: authenticate, validate, authorize, act. Use correct status codes: `201` created, `204` no content, `400` bad input, `401` not signed in, `403` not allowed, `404` missing, `429` rate limited.

Never send internal error messages to the client. Log them on the server.

## Caching

Route Handlers are **not cached by default**. Only `GET` can be cached; other methods never are, even if they sit in the same file as a cached `GET`.

### Previous model (no Cache Components)

Opt a `GET` into static output with route segment config:

```ts
export const dynamic = "force-static";

export async function GET() {
  return Response.json(await fetchPublicData());
}
```

### With Cache Components

`GET` handlers follow the same rules as pages: they run at request time by default, and are **prerendered** only if they touch nothing request-specific or uncached.

| The handler... | Result |
|---|---|
| Returns only constants | Prerendered at build time |
| Calls `Math.random()`, `Date.now()`, a DB or `fetch` without caching | Runs at request time |
| Reads `headers()`, `cookies()`, `request.url`, `request.headers`, `request.cookies`, `request.body`, or `connection()` | Runs at request time |
| Calls a helper marked `"use cache"` | Cached result can be part of the prerendered response |

```ts
import { cacheLife } from "next/cache";

export async function GET() {
  return Response.json(await getProducts());
}

async function getProducts() {
  "use cache";            // goes on the helper, not in the handler body
  cacheLife("hours");
  return db.product.findMany();
}
```

`"use cache"` cannot go directly inside the handler body; extract a helper. See [Cache Components](../06-caching/05-cache-components.md).

Segment config exports like `dynamic`, `revalidate` and `fetchCache` do not apply under Cache Components; see the migration table in that note.

## Streaming

Return a `ReadableStream` for server-sent events, LLM output or large exports:

```ts
export async function GET() {
  const encoder = new TextEncoder();
  const stream = new ReadableStream({
    async start(controller) {
      for (let i = 1; i <= 3; i++) {
        controller.enqueue(encoder.encode(`data: tick ${i}\n\n`));
        await new Promise((r) => setTimeout(r, 500));
      }
      controller.close();
    },
  });

  return new Response(stream, {
    headers: { "Content-Type": "text/event-stream", "Cache-Control": "no-cache" },
  });
}
```

Hosts that run handlers as short-lived functions can cut off long streams. Check your platform's duration limits.

## Non-UI responses

```ts
// app/rss.xml/route.ts  →  /rss.xml
export async function GET() {
  const posts = await getPosts();
  const items = posts
    .map((p) => `<item><title>${escapeXml(p.title)}</title><link>https://example.com/blog/${p.slug}</link></item>`)
    .join("");

  return new Response(
    `<?xml version="1.0" encoding="UTF-8"?><rss version="2.0"><channel><title>Blog</title>${items}</channel></rss>`,
    { headers: { "Content-Type": "application/xml" } },
  );
}
```

Escape or sanitize any value you put into markup. `sitemap.xml`, `robots.txt`, `manifest`, icons and Open Graph images have dedicated file conventions; use those instead of a handler.

## Calling handlers: what not to do

- **Do not call your own Route Handler from a Server Component.** At build time no server is listening, so the build fails; at runtime it adds a network hop. Call the shared function directly. See [Server Fetching](../05-data-fetching/00-server-fetching.md).
- **Do not use handlers for your own form mutations.** Server Actions do the same job with built-in cache refresh.
- **Do not use Server Actions as a public API.** Actions are for your UI, dispatched sequentially and not designed for third parties.

## Deployment notes

Some hosts run handlers as serverless functions. That means:

- No shared memory between requests (module-level state is unreliable).
- The filesystem may be read-only or ephemeral.
- Long requests can hit a timeout.
- WebSockets do not work inside a Route Handler.

With `output: "export"` (static export), only `GET` handlers are supported and they must be static (`dynamic = "force-static"` on the previous model). Cache Components does not support static export.

## Common mistakes

| Mistake | Symptom | Fix |
|---|---|---|
| `route.ts` next to `page.tsx` | Build error / conflict | Move the handler to a different segment such as `api/` |
| Forgetting to `await params` | `id` is `undefined` or a Promise | `const { id } = await ctx.params` |
| No auth on a "private" endpoint | Anyone can call it | Authenticate in the handler |
| `request.json()` on invalid JSON | Unhandled 500 | Wrap in `try/catch`, return `400` |
| Reading the body twice | Error: body already used | `request.clone()` first |
| Returning raw error messages | Internals leak | Log, return a generic message |
| Expecting `POST` responses to be cached | They never are | Cache on the read path |
| Fetching your own handler from a Server Component | Build fails | Call the underlying function |
| `use cache` directly in the handler | Error | Move it to a helper function |
| Assuming a `GET` is static under Cache Components | Runs per request | Remove request-time reads or use `use cache` |
| `redirect()` inside a `try/catch` in a handler | The redirect is swallowed (it works by throwing) | Call it outside the `try`, or return `NextResponse.redirect(...)` |

## Quick Summary

- `route.ts` exports method functions (`GET`, `POST`, ...) and uses the Web `Request`/`Response` APIs.
- A segment has a `page` **or** a `route`, never both.
- `params` is a Promise; `RouteContext` types it.
- Handlers are public: authenticate, validate, return correct status codes, keep errors generic.
- Not cached by default; only `GET` can be cached, via `force-static` (previous model) or `use cache` helpers (Cache Components).
- Use Server Actions for your own UI and Server Components for reads; handlers are for outside callers and non-UI output.
