# 00 · Internationalization (i18n)

Serving the same app in several languages: locale-prefixed URLs, translated strings and locale-aware rendering. Next.js gives you the routing pieces; translation is plain data loading (or a library).

> Verified against the Next.js 16.4 Internationalization guide. Library comparisons and message-format advice are general knowledge and labelled as such. The App Router has no built-in `i18n` config (that was a Pages Router feature), so everything here is built from a dynamic segment, `proxy.ts` and your own dictionaries.

## 1. What

Two separate problems:

| Problem | Name | Next.js piece |
|---|---|---|
| Which language does this URL serve? | Internationalized routing | `app/[lang]/...` + `proxy.ts` redirect |
| What are the words in that language? | Localization | Dictionary files + a loader |

Routing can be by sub-path (`/fr/products`) or by domain (`my-site.fr/products`). This note builds the sub-path version, which is what the docs show.

## 2. Why

- Users and search engines get a stable URL per language.
- Locale in the URL means pages can be statically generated per language and cached.
- Dictionaries loaded on the server never enter the client bundle, so translation size does not affect JavaScript size.

## 3. How

### 3.1 Structure

```text
app/
└── [lang]/
    ├── layout.tsx
    ├── page.tsx
    ├── dictionaries.ts
    └── dictionaries/
        ├── en.json
        └── nl.json
proxy.ts
```

Every special file (layout, page, loading, error, and so on) goes under `app/[lang]`. The router then passes `lang` to every layout and page. The root layout may itself live in `app/[lang]/layout.tsx`.

### 3.2 Detect the locale in `proxy.ts`

The docs pick the locale from the `Accept-Language` header using `negotiator` and `@formatjs/intl-localematcher`:

```bash
npm install negotiator @formatjs/intl-localematcher
npm install -D @types/negotiator
```

```ts
// proxy.ts
import { NextResponse, type NextRequest } from 'next/server'
import { match } from '@formatjs/intl-localematcher'
import Negotiator from 'negotiator'

const locales = ['en', 'nl']
const defaultLocale = 'en'

function getLocale(request: NextRequest) {
  const headers = { 'accept-language': request.headers.get('accept-language') ?? '' }
  const languages = new Negotiator({ headers }).languages()
  return match(languages, locales, defaultLocale)
}

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  const hasLocale = locales.some(
    (l) => pathname === `/${l}` || pathname.startsWith(`/${l}/`)
  )
  if (hasLocale) return

  const locale = getLocale(request)
  request.nextUrl.pathname = `/${locale}${pathname}`
  return NextResponse.redirect(request.nextUrl)
}

export const config = {
  // Skip internal paths. Also skip API routes and static files in a real app.
  matcher: ['/((?!_next|api|.*\\..*).*)'],
}
```

The docs' matcher is `'/((?!_next).*)'`. The version above also excludes `api` and anything with a file extension so images, `favicon.ico`, `robots.txt` and `sitemap.xml` are not redirected to `/en/...`. That widening is common practice, not from the docs, so adjust it to your routes.

Notes:

- `proxy.ts` is the Next.js 16 name for what used to be `middleware.ts`. It runs before the route renders, so redirects here keep real HTTP status codes.
- A cookie that remembers the user's explicit choice is a common extension (read it before `Accept-Language`). The docs only show the header.
- Use short locale codes (`en`, `nl`) or region codes (`en-US`), but be consistent: the folder segment, the dictionary keys, `generateStaticParams` and the matcher list must all agree.

### 3.3 Dictionaries

```json
// app/[lang]/dictionaries/en.json
{ "products": { "cart": "Add to Cart" } }
```

```json
// app/[lang]/dictionaries/nl.json
{ "products": { "cart": "Toevoegen aan Winkelwagen" } }
```

```ts
// app/[lang]/dictionaries.ts
import 'server-only'

const dictionaries = {
  en: () => import('./dictionaries/en.json').then((m) => m.default),
  nl: () => import('./dictionaries/nl.json').then((m) => m.default),
}

export type Locale = keyof typeof dictionaries

export const hasLocale = (locale: string): locale is Locale =>
  locale in dictionaries

export const getDictionary = async (locale: Locale) => dictionaries[locale]()
```

- `import 'server-only'` makes the build fail if a Client Component imports this file.
- Dynamic `import()` means only the requested language is loaded.
- `hasLocale` is a type guard: `params.lang` is typed `string`, and the guard narrows it to your supported locales.

### 3.4 Use it in a page

```tsx
// app/[lang]/page.tsx
import { notFound } from 'next/navigation'
import { getDictionary, hasLocale } from './dictionaries'

export default async function Page({ params }: PageProps<'/[lang]'>) {
  const { lang } = await params
  if (!hasLocale(lang)) notFound()

  const dict = await getDictionary(lang)
  return <button>{dict.products.cart}</button>
}
```

`notFound()` for an unknown locale returns a 404 instead of a runtime crash from a missing dictionary.

### 3.5 Reading the locale anywhere: `next/root-params`

Passing `lang` down every layer gets tedious. Because every route sits under `app/[lang]`, `lang` is a **root parameter**, and `next/root-params` exports a getter for it:

```ts
// app/[lang]/dictionaries.ts
import { lang } from 'next/root-params'
import { notFound } from 'next/navigation'

const dictionaries = {
  en: () => import('./dictionaries/en.json').then((m) => m.default),
  nl: () => import('./dictionaries/nl.json').then((m) => m.default),
}

export const hasLocale = (l: string): l is keyof typeof dictionaries =>
  l in dictionaries

export const getDictionary = async () => {
  const locale = await lang()
  if (!hasLocale(locale)) notFound()
  return dictionaries[locale]()
}
```

```tsx
const dict = await getDictionary() // no argument
```

Constraints from the docs:

- Works in Server Components and server-side utilities.
- **Does not work** in Client Components, Server Actions or Route Handlers.
- No `import 'server-only'` needed; importing it in a Client Component fails at build time.

### 3.6 Static rendering per locale

```tsx
// app/[lang]/layout.tsx
export async function generateStaticParams() {
  return [{ lang: 'en' }, { lang: 'nl' }]
}

export default async function RootLayout({
  children,
  params,
}: LayoutProps<'/[lang]'>) {
  return (
    <html lang={(await params).lang}>
      <body>{children}</body>
    </html>
  )
}
```

Setting `<html lang>` matters for accessibility and for search engines.

### 3.7 Language switcher and SEO links

A switcher is a normal `Link` to the same path under another locale. For search engines, declare alternates in metadata (see [14 · Metadata](../14-seo-and-metadata/00-metadata.md) and the sitemap `alternates.languages` field in [02 · Sitemap and Robots](../14-seo-and-metadata/02-sitemap-and-robots.md)):

```tsx
export async function generateMetadata(props: PageProps<'/[lang]'>): Promise<Metadata> {
  const { lang } = await props.params
  return {
    alternates: {
      canonical: `/${lang}`,
      languages: { en: '/en', nl: '/nl' },
    },
  }
}
```

### 3.8 Client Components

Dictionaries are server-only. Pass the strings a Client Component needs as props, or pass just the slice it uses:

```tsx
<AddToCart label={dict.products.cart} />
```

Do not provide the whole dictionary through a client context unless you accept shipping it to the browser.

### 3.9 Formatting numbers, dates, plurals

This is general knowledge, not from the Next.js docs. Use the built-in `Intl` APIs with the locale string:

```ts
new Intl.NumberFormat(lang, { style: 'currency', currency: 'EUR' }).format(1234.5)
new Intl.DateTimeFormat(lang, { dateStyle: 'long' }).format(date)
new Intl.PluralRules(lang).select(count) // 'one' | 'other' | ...
```

Plural rules differ by language (some have more than two forms), which is why `count === 1 ? ... : ...` breaks in other languages.

## 4. When

| Situation | Choice |
|---|---|
| 2 to 5 languages, plain strings | The docs' dictionaries pattern |
| Plurals, interpolation, rich text, many locales | A library; the docs list `next-intl`, `next-international`, `next-i18n-router`, `paraglide-next`, `lingui`, `tolgee`, `next-intlayer`, `gt-next` |
| Different domain per language | Domain routing, handled in your proxy or at the host |
| One language only | Skip all of this |

Check that a library supports the App Router, Server Components and `proxy.ts` on your Next.js version before adopting it.

## 5. Practical

1. Move `app/*` under `app/[lang]/`.
2. Add `proxy.ts` and test: `curl -I localhost:3000/` returns a redirect to `/en`.
3. Add two dictionaries and `getDictionary`.
4. Add `generateStaticParams` and `<html lang>`.
5. Add a switcher and `alternates.languages`.
6. Check that `/xx` (unknown locale) returns 404.

## Common mistakes

| Mistake | Effect | Fix |
|---|---|---|
| Some routes left outside `app/[lang]` | They are not localized or conflict with the redirect | Move every special file |
| Proxy matcher catches static files | Images and `robots.txt` redirect to `/en/...` | Exclude them in `matcher` |
| Locale list differs between proxy, dictionaries and `generateStaticParams` | 404s or redirect loops | One shared constant |
| No `hasLocale` check | Crash on `/foo/` treated as a locale | `hasLocale` + `notFound()` |
| Importing dictionaries in a Client Component | Build error, or bundle bloat | Pass strings as props |
| Using root-params getter in a Server Action or Route Handler | Not supported | Pass the locale in explicitly |
| Missing `<html lang>` | Poor accessibility and SEO | Set from `params` |
| Hard-coded `en-US` formatting | Wrong dates and currency | `Intl` with the active locale |
| Redirect loop | Proxy redirects a path that already has a locale | The `hasLocale` early return must match your segment format |

## Debugging

```text
Wrong or looping locale
  ├─ curl -I with and without -H "Accept-Language: nl"   → expected redirect?
  ├─ Path already has a locale prefix but still redirects → early-return check
  ├─ 404 on a valid locale                                → hasLocale keys vs folder names
  └─ Static files redirected                              → matcher
Page shows English only
  └─ lang not reaching the loader                         → await params, or root-params getter
```

## Quick Summary

- Routing: `app/[lang]` plus a `proxy.ts` redirect that picks the locale from `Accept-Language`.
- Localization: JSON dictionaries loaded by a `server-only` function; unknown locale gives `notFound()`.
- `next/root-params` removes prop drilling for `lang` in server code, but not in Client Components, Actions or Route Handlers.
- `generateStaticParams` prerenders each locale; set `<html lang>`.
- Add `alternates.languages` for SEO and use `Intl` for formatting.
