# Routes and Params

Routes carry data in three places: dynamic segments (`params`), the query string (`searchParams`) and the path itself (links and redirects). This note shows how to type each, how Next.js's generated helpers do most of the work, and where you still need runtime validation.

> Verified against the Next.js 16.4 `page`, `layout`, `route`, `generateMetadata` and TypeScript references, and the `typedRoutes` option.

## What it is

Since Next.js 15, `params` and `searchParams` are **Promises**, because they are request-time data. The types below reflect that. Next.js also generates route-aware global helpers so you do not hand-write param shapes:

| Helper | For | Needs import? |
|---|---|---|
| `PageProps<'/route'>` | `page.tsx` props | No (global) |
| `LayoutProps<'/route'>` | `layout.tsx` props, including parallel-route slots | No (global) |
| `RouteContext<'/route'>` | Route Handler second argument | No (global) |

They are generated by `next dev`, `next build` or `next typegen`. Until types are generated once, the editor will not know them.

## Typing `params`

### Manual

```tsx
// app/shop/[slug]/page.tsx
export default async function Page({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params;
  return <h1>{slug}</h1>;
}
```

### With the helper (preferred)

```tsx
export default async function Page(props: PageProps<"/blog/[slug]">) {
  const { slug } = await props.params;          // typed from the route literal
  const query = await props.searchParams;
  return <h1>Blog Post: {slug}</h1>;
}
```

Using a literal route string enables autocomplete and strict keys. Static routes resolve `params` to `{}`.

### Shapes per segment kind

From the docs' tables:

| File | URL | `params` |
|---|---|---|
| `app/shop/[slug]/page.tsx` | `/shop/1` | `Promise<{ slug: string }>` |
| `app/shop/[category]/[item]/page.tsx` | `/shop/1/2` | `Promise<{ category: string; item: string }>` |
| `app/shop/[...slug]/page.tsx` | `/shop/1/2` | `Promise<{ slug: string[] }>` |
| `app/shop/[[...slug]]/page.tsx` (optional catch-all) | `/shop` | `Promise<{ slug?: string[] }>` |

Params are always **strings** (or string arrays): `/posts/42` gives `"42"`, not `42`. Convert and validate:

```tsx
const { id } = await props.params;
const postId = Number(id);
if (!Number.isInteger(postId)) notFound();      // from "next/navigation"
```

The optional catch-all row is standard Next.js dynamic-route behavior, not copied from the page reference table.

### Layouts and route handlers

```tsx
// app/dashboard/[team]/layout.tsx
export default async function Layout(props: LayoutProps<"/dashboard/[team]">) {
  const { team } = await props.params;
  return <section>{props.children}</section>;
}
```

Parallel route slots appear as typed props. With `app/dashboard/@analytics`, `LayoutProps<"/dashboard">` exposes `props.analytics`.

```ts
// app/users/[id]/route.ts
import type { NextRequest } from "next/server";

export async function GET(_req: NextRequest, ctx: RouteContext<"/users/[id]">) {
  const { id } = await ctx.params;
  return Response.json({ id });
}
```

Without the helper: `{ params }: { params: Promise<{ id: string }> }`.

### Client Component pages

A Client Component cannot be `async`; unwrap with `use()`:

```tsx
"use client";

import { use } from "react";

export default function Page({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = use(params);
  return <p>{slug}</p>;
}
```

Elsewhere in the client tree use the hooks, which return values (not Promises): `useParams<{ slug: string }>()`, `usePathname()`, `useSearchParams()`. Check your Next.js version's `useParams` reference for its generic signature.

## Typing `searchParams`

```tsx
export default async function Page({
  searchParams,
}: {
  searchParams: Promise<{ [key: string]: string | string[] | undefined }>
}) {
  const { page = "1", sort = "asc", query = "" } = await searchParams;
  /* page: string | string[] — still not a number */
}
```

`searchParams` is a plain object, not a `URLSearchParams`. A key repeated in the URL (`?a=1&a=2`) becomes `string[]`, and a missing key is `undefined`, so every value is `string | string[] | undefined`. The type tells you the shape of the container, **not** that the value is valid. Parse it:

```ts
// app/lib/search-params.ts
import * as z from "zod";

const ProductQuery = z.object({
  q: z.string().trim().max(100).catch(""),
  sort: z.enum(["new", "price-asc", "price-desc"]).catch("new"),
  page: z.coerce.number().int().min(1).catch(1),
});

export type ProductQuery = z.infer<typeof ProductQuery>;

export function parseProductQuery(raw: Record<string, string | string[] | undefined>): ProductQuery {
  const first = (v: string | string[] | undefined) => (Array.isArray(v) ? v[0] : v);
  return ProductQuery.parse({ q: first(raw.q), sort: first(raw.sort), page: first(raw.page) });
}
```

```tsx
export default async function Page(props: PageProps<"/products">) {
  const { q, sort, page } = parseProductQuery(await props.searchParams);   // fully typed and safe
  const products = await getProducts({ q, sort, page });
  /* ... */
}
```

`.catch(default)` keeps the page rendering when someone hand-edits the URL; use `.parse` errors instead if you want a 400 or `notFound()`. Reading `searchParams` opts the page into request-time rendering, and under Cache Components where you read it decides how much can be prerendered ([Dynamic Rendering](../04-rendering/02-dynamic-rendering.md)).

## Typed links (`typedRoutes`)

Enable once:

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = { typedRoutes: true };   // stable; not experimental.typedRoutes
export default nextConfig;
```

Next.js generates a definition of every route under `.next/types` (included via `tsconfig`), and the compiler then validates links:

```tsx
"use client";

import type { Route } from "next";
import Link from "next/link";
import { useRouter } from "next/navigation";

export function Examples({ slug }: { slug: string }) {
  const router = useRouter();
  return (
    <>
      <Link href="/about" />                            {/* OK */}
      <Link href={`/blog/${slug}`} />                   {/* OK: template literal validated against /blog/[slug] */}
      <Link href="/aboot" />                            {/* TypeScript error: not a route */}
      <Link href={("/blog/" + slug) as Route} />        {/* non-literal: cast needed */}
      <button onClick={() => router.push("/about")}>Go</button>
    </>
  );
}
```

Facts from the docs:

- Works for `next/link` `href` and for `next/navigation` `push`, `replace` and `prefetch` in the App Router. It does **not** type `next/router` in the Pages Router.
- **Literal** strings (including template literals with dynamic segments) are validated; **non-literal** strings need `as Route`.
- Routes created by **Proxy redirects** or rewrites are not in the route list, so link to them with `as Route`.

Wrapper components take a generic:

```tsx
import type { Route } from "next";
import Link from "next/link";

function Card<T extends string>({ href }: { href: Route<T> | URL }) {
  return <Link href={href}><div>My Card</div></Link>;
}
```

A typed list of links:

```ts
import type { Route } from "next";

type NavItem<T extends string = string> = { href: T; label: string };

export const navItems: NavItem<Route>[] = [
  { href: "/", label: "Home" },
  { href: "/about", label: "About" },
];
```

Keep route-building in one place so a renamed route is a compile error everywhere:

```ts
export const paths = {
  home: "/",
  post: (slug: string) => `/blog/${slug}` as const,     // literal template type
} as const;
```

(With `as const` the template stays a literal type, so `typedRoutes` can validate it.)

## Typing metadata

```tsx
import type { Metadata } from "next";

export async function generateMetadata(props: PageProps<"/products/[id]">): Promise<Metadata> {
  const { id } = await props.params;
  const product = await getProduct(id);
  return { title: product.name };
}
```

The docs' longer form defines `type Props = { params: Promise<{ id: string }>; searchParams: Promise<...> }` and a second `parent: ResolvingMetadata` argument imported from `next` to read parent metadata. The docs also say you can type the first argument with `PageProps<'/route'>` or `LayoutProps<'/route'>` for completion. Static metadata: `export const metadata: Metadata = { ... }`. Both exports work only in Server Components.

## Typing Route Handlers

```ts
// app/api/posts/route.ts
import type { NextRequest } from "next/server";
import * as z from "zod";

const CreatePost = z.object({ title: z.string().min(1).max(200), body: z.string() });

export async function POST(request: NextRequest) {
  const json: unknown = await request.json();                 // unknown, not any
  const parsed = CreatePost.safeParse(json);
  if (!parsed.success) return Response.json({ errors: parsed.error.flatten().fieldErrors }, { status: 400 });

  const { title, body } = parsed.data;                         // typed
  return Response.json({ ok: true }, { status: 201 });
}

export async function GET(request: NextRequest) {
  const q = request.nextUrl.searchParams.get("query");        // string | null
  return Response.json({ q });
}
```

`request.json()` returns `Promise<any>` in the Web API typing; assigning to `unknown` forces a parse. `NextRequest` adds `nextUrl` and `cookies` to the Web `Request`. A JSON response cannot carry a `Date` or `bigint`: the client receives a string or the call throws, so type response bodies as their JSON form.

To share the response type with a client `fetch`:

```ts
// app/api/posts/route.ts
export type PostsResponse = { posts: { id: string; title: string }[] };
// client
const data = (await res.json()) as PostsResponse;     // an assertion; validate if the source is untrusted
```

Inside your own app, calling the DAL from a Server Component or Server Action avoids this problem entirely.

## Environment variables

`process.env.X` is `string | undefined`. Validate once and export typed values:

```ts
// app/lib/env.ts
import "server-only";
import * as z from "zod";

const Env = z.object({
  DATABASE_URL: z.url(),
  SESSION_SECRET: z.string().min(32),
});

export const env = Env.parse(process.env);       // throws at start-up with a clear error
```

`experimental.typedEnv: true` additionally generates editor types in `.next/types` for variables loaded during development (it is experimental, and production-only variables are excluded unless you run `next dev` with `NODE_ENV=production`). It gives IntelliSense, not validation.

## CI

```bash
next typegen && tsc --noEmit
```

Run this before merging. Without `typegen`, route helpers and typed links are not available to a bare `tsc`.

## Debugging

| Symptom | Likely cause | Fix |
|---|---|---|
| `Cannot find name 'PageProps'` | Types not generated yet | Run `next dev`, `next build` or `next typegen` once; check `.next/types/**/*.ts` is in `include` |
| `Property 'slug' does not exist on type 'Promise<...>'` | Forgot to `await` / `use()` | `const { slug } = await props.params` |
| Type error on `<Link href={...}>` for a valid URL | Non-literal string, or a Proxy-created route | `as Route` |
| `typedRoutes` seems ignored | Option not enabled, or not using TypeScript | Enable it at top level in `next.config.ts` |
| Runtime `params.id` is `"42"`, code expects a number | Params are strings | Convert and validate |
| `searchParams.page` typed as `string \| string[] \| undefined` | By design | Parse with a schema |
| CI `tsc` fails on route helpers but dev works | No generated types in CI | `next typegen && tsc --noEmit` |
| `next typegen` fails to load config | Config needs env vars or deps not present | Provide them |
| Stale route types after renaming folders | Generated types not refreshed | Re-run dev or typegen |
| Async page: `Promise<Element>` JSX error | Old TS / `@types/react` | Upgrade |

## Common mistakes

| Mistake | Fix |
|---|---|
| Typing `params` as a plain object (Next 14 style) | `Promise<{ ... }>` and `await` |
| Hand-writing param shapes everywhere | `PageProps<'/route'>` etc. |
| Assuming query values are valid numbers or enums | Validate with a schema |
| Casting JSON bodies with `as` | `unknown` plus schema `parse` |
| Scattered string URLs | A `paths` helper plus `typedRoutes` |
| Silencing link errors with `as Route` on literals | Fix the route; cast only truly non-literal strings |
| Reading `searchParams` high in the tree under Cache Components | Read it in the smallest dynamic component |
| Disabling build type errors to ship | Fix them, or type-check separately in CI |

## Quick Summary

- `params` and `searchParams` are Promises; `await` them, or `use()` them in Client Components.
- Prefer `PageProps<'/route'>`, `LayoutProps<'/route'>` and `RouteContext<'/route'>`; they are global and generated by `next dev`, `build` or `typegen`.
- Turn on `typedRoutes` so `Link` and `router.push` reject unknown routes; cast non-literal strings with `as Route`.
- Types describe shape, not validity: parse params, `searchParams`, bodies and env vars with a schema.
- Run `next typegen && tsc --noEmit` in CI.
