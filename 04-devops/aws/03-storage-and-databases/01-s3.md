## 1. What & Why

Amazon Simple Storage Service (Amazon S3) is an industry-leading object storage service offering virtually unlimited scalability, data availability, security, and performance. Unlike traditional block storage (EBS) or file system storage (EFS) that manage data as sectors or hierarchical directories, S3 stores data as **objects** composed of a file payload, unique key, and comprehensive metadata.

Amazon S3 forms the bedrock of modern cloud architecture:
- **Durability Guarantee**: Engineered for **99.999999999% (11 9's)** of data durability by automatically replicating objects across a minimum of three physically separated Availability Zones.
- **Unbounded Capacity**: Stores exabytes of data across trillions of objects without manual disk volume provisioning, filesystem formatting, or storage capacity planning.
- **Foundational Integration**: Serves as the primary data lake store for big data analytics (Amazon Athena, EMR, Redshift Spectrum), backup archives, static web hosting, and container image registries.
- **Zero-Trust Security**: Features centralized **Block Public Access**, granular Bucket Policies, Access Control Lists (ACLs disabled by default), and automatic default server-side encryption (SSE-S3 / SSE-KMS).

## 2. Core Concepts

### 2.1 Buckets and Objects
- **Bucket**: A top-level container for objects. Bucket names reside in a **globally unique namespace** across all AWS accounts worldwide (e.g., `s3://my-unique-bucket-name/`).
- **Object**: A file and its associated metadata:
  - **Key**: The full path name identifying the object within the bucket (e.g., `photos/2026/november/vacation.jpg`).
  - **Value**: The binary file payload (size from 0 bytes up to **5 TB** per individual object).
  - **Version ID**: Distinguishes revisions when S3 Versioning is enabled.
  - **Metadata**: System metadata (e.g., `Content-Type`, `Last-Modified`) and custom user-defined key-value tags.

### 2.2 S3 Storage Classes
S3 provides tiered storage classes optimized for varying data access patterns and cost structures:
- **S3 Standard**: Default class for active, frequently accessed data. Low latency (single-digit milliseconds), high throughput, no minimum storage duration or retrieval fees.
- **S3 Intelligent-Tiering**: Automatically moves objects between access tiers (Frequent, Infrequent, Archive Instant, Deep Archive) based on actual access patterns without retrieval fees or operational overhead.
- **S3 Standard-Infrequent Access (Standard-IA)**: Lower storage cost for data accessed less frequently but requiring immediate millisecond retrieval. Incurs retrieval fees per GB.
- **S3 One Zone-IA**: Stores data in a single Availability Zone for a 20% storage cost reduction. Durability is 11 9's within the AZ, but data is lost if the AZ is destroyed.
- **S3 Glacier Instant Retrieval**: Lowest storage cost for long-term archives requiring millisecond access.
- **S3 Glacier Flexible Retrieval**: Archive storage with retrieval times from 1–5 minutes (Expedited) to 3–5 hours (Standard). Free bulk retrieval.
- **S3 Glacier Deep Archive**: Lowest-cost storage class in AWS (~$0.00099 per GB/month). Designed for regulatory compliance archiving with 12–48 hour retrieval times.

### 2.3 Security Controls & Public Access
- **S3 Block Public Access**: Account-level and bucket-level master switch that overrides all bucket policies and ACLs, guaranteeing no public internet exposure. Enabled by default on all new buckets.
- **Bucket Policies**: JSON identity policies attached directly to the bucket resource controlling permissions for principals, IP CIDR ranges, VPC Endpoints, and encryption enforcement.
- **Presigned URLs**: Grants temporary, time-limited download or upload access to private S3 objects using the creator's IAM credentials, without modifying bucket policies or making objects public.

### Strong Read-After-Write Consistency Model
Since December 2020, Amazon S3 provides **strong read-after-write consistency** out of the box for `PUT` and `DELETE` requests of objects across all regions:
- After a successful `PUT` of a new object or an overwrite of an existing object, any subsequent `GET` or `LIST` request immediately returns the latest version.
- Eliminates the need for external caching layers (such as S3Guard) previously required by big data query engines.

## 4. Syntax & Usage

### 4.1 Creating a Hardened S3 Bucket via AWS CLI
```bash
# 1. Create bucket (regions outside us-east-1 require LocationConstraint)
aws s3api create-bucket \
  --bucket prod-enterprise-data-vault-111122223333 \
  --region us-east-1

# 2. Enforce S3 Block Public Access (All 4 settings enabled)
aws s3api put-public-access-block \
  --bucket prod-enterprise-data-vault-111122223333 \
  --public-access-block-configuration '{
    "BlockPublicAcls": true,
    "IgnorePublicAcls": true,
    "BlockPublicPolicy": true,
    "RestrictPublicBuckets": true
  }'

# 3. Enable S3 Versioning
aws s3api put-bucket-versioning \
  --bucket prod-enterprise-data-vault-111122223333 \
  --versioning-configuration Status=Enabled

# 4. Enforce Default Server-Side Encryption with KMS (SSE-KMS)
aws s3api put-bucket-encryption \
  --bucket prod-enterprise-data-vault-111122223333 \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms",
        "KMSMasterKeyId": "arn:aws:kms:us-east-1:111122223333:alias/s3-data-key"
      },
      "BucketKeyEnabled": true
    }]
  }'
```

### 4.2 Generating a Presigned URL for Temporary Client Upload
```bash
# Generate a presigned URL valid for 15 minutes (900 seconds) for object upload
aws s3 presign \
  s3://prod-enterprise-data-vault-111122223333/incoming/report.pdf \
  --expires-in 900
```

## 5. Practical Examples

### Example 1: Enforcing HTTPS-Only and Secure Transport via Bucket Policy
Bucket policy that strictly denies any unencrypted HTTP request (`aws:SecureTransport = false`).

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceTLSRequestsOnly",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::prod-enterprise-data-vault-111122223333",
        "arn:aws:s3:::prod-enterprise-data-vault-111122223333/*"
      ],
      "Condition": {
        "Bool": {
          "aws:SecureTransport": "false"
        }
      }
    }
  ]
}
```

Apply via CLI:
```bash
aws s3api put-bucket-policy \
  --bucket prod-enterprise-data-vault-111122223333 \
  --policy file://deny-http-policy.json
```

### Example 2: Declarative Terraform S3 Bucket with Lifecycle Rules
Automated lifecycle transitions from S3 Standard to Intelligent-Tiering and Glacier Deep Archive, with noncurrent version expiration.

```hcl
resource "aws_s3_bucket" "data_lake" {
  bucket = "prod-analytics-lake-111122223333"

  lifecycle {
    prevent_destroy = true
  }
}

resource "aws_s3_bucket_versioning" "versioning" {
  bucket = aws_s3_bucket.data_lake.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_public_access_block" "block_public" {
  bucket = aws_s3_bucket.data_lake.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_lifecycle_configuration" "lifecycle" {
  bucket = aws_s3_bucket.data_lake.id

  rule {
    id     = "tiering-and-archival-policy"
    status = "Enabled"

    filter {
      prefix = "raw-logs/"
    }

    # Transition current objects to S3 Intelligent-Tiering after 30 days
    transition {
      days          = 30
      storage_class = "INTELLIGENT_TIERING"
    }

    # Transition current objects to Glacier Deep Archive after 180 days
    transition {
      days          = 180
      storage_class = "DEEP_ARCHIVE"
    }

    # Clean up noncurrent versions after 90 days to control storage cost
    noncurrent_version_expiration {
      noncurrent_days = 90
    }

    # Abort failed multipart uploads after 7 days
    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }
}
```

### Example 3: Multipart Upload for Large Files via AWS CLI & SDK
Files larger than 100 MB must be uploaded using **S3 Multipart Upload** to achieve parallel throughput and network fault recovery.

```bash
# AWS CLI high-level s3 commands automatically perform multipart uploads for files > 8MB
aws s3 cp large-database-dump.sql s3://prod-enterprise-data-vault-111122223333/backups/ \
  --storage-class STANDARD_IA
```

Python Boto3 script generating a presigned upload URL:
```python
import boto3

def generate_presigned_upload_url(bucket_name, object_key, expiration=3600):
    s3_client = boto3.client('s3')
    response = s3_client.generate_presigned_post(
        Bucket=bucket_name,
        Key=object_key,
        Fields={"acl": "private"},
        Conditions=[
            {"acl": "private"},
            ["content-length-range", 10, 104857600] # Min 10B, Max 100MB
        ],
        ExpiresIn=expiration
    )
    return response
```

Amazon S3 automatically scales to support **3,500 PUT/POST/DELETE** and **5,500 GET** requests per second **per prefix**:

## 6. Best Practices

1. **Enable S3 Bucket Keys when Using SSE-KMS**: Always configure `BucketKeyEnabled = true`. S3 Bucket Keys reduce KMS request traffic from S3 by up to **99%**, saving thousands of dollars per month on AWS KMS API request costs.
2. **Always Configure `AbortIncompleteMultipartUpload`**: When multipart uploads fail mid-stream or are abandoned, the uploaded parts remain stored in the bucket indefinitely and incur monthly storage fees. Add a lifecycle rule to abort incomplete uploads after 7 days.
3. **Adopt S3 Intelligent-Tiering for Unpredictable Data**: For datasets with unknown or fluctuating access patterns, use S3 Intelligent-Tiering. It automatically moves unaccessed data to cheaper tiers with zero retrieval charges and zero operational risk.
4. **Enforce `aws:SecureTransport` on All Bucket Policies**: Guarantee all data in transit is encrypted using TLS 1.2+ by adding an explicit `Deny` condition for non-HTTPS connections.
5. **Disable S3 Access Control Lists (ACLs)**: Use the **Bucket Owner Enforced** object ownership setting (`ObjectOwnership = BucketOwnerEnforced`). This disables legacy S3 ACLs completely and centralizes access governance exclusively under AWS IAM and Bucket Policies.

## 7. Common Mistakes

| Mistake | Consequence | Correct Pattern |
|:---|:---|:---|
| **Disabling S3 Block Public Access** | Accidental data leaks exposing confidential company databases and documents to internet crawlers. | Keep all 4 S3 Block Public Access flags enabled at both account and bucket levels. |
| **Omitting KMS Bucket Keys** | Massive AWS KMS bills ($0.03 per 10k requests) during heavy S3 analytics or data lake queries. | Enable **S3 Bucket Keys** (`BucketKeyEnabled = true`) on all SSE-KMS encrypted buckets. |
| **Forgetting to Clean Up Noncurrent Versions** | S3 Versioning stores every overwritten/deleted file revision indefinitely, quietly multiplying storage bills. | Configure lifecycle rules with `noncurrent_version_expiration` (e.g., expire after 30–90 days). |
| **Storing Small Files (<128 KB) in Infrequent Access** | High per-request overhead; S3 charges a minimum 128 KB storage capacity charge for IA and Glacier objects. | Keep small files in S3 Standard or combine them into larger archive archives (Parquet/Zip) before tiering. |
| **Using S3 Standard-IA for Active Data** | S3 Standard-IA charges $0.01 per GB retrieved. High-frequency reads result in exorbitant data retrieval fees. | Reserve Infrequent Access for backups and disaster recovery data accessed less than once a month. |
| **Hardcoding Public URLs for App Uploads** | Bypasses authentication; clients either fail with 403 Forbidden or bucket must be dangerously made public. | Generate short-lived **Presigned URLs** from your backend API for direct client uploads. |

## 8. Performance, Security & Cost Notes

### Throughput Scaling Limits
- **Per-Prefix Capacity**: S3 supports **3,500 PUT/COPY/POST/DELETE** and **5,500 GET/HEAD** requests per second per prefix.
- Adding distinct prefixes (e.g., `s3://bucket/folder1/` vs `s3://bucket/folder2/`) scales throughput linearly. There is no limit to the number of prefixes in a bucket.

### Security Enforcements
- **Encryption by Default**: Since January 2023, Amazon S3 automatically encrypts all new objects with SSE-S3 (AES-256) at zero additional cost.
- **TLS 1.2+ Requirement**: AWS S3 enforces TLS 1.2 or higher for all REST API connections.

### Storage Pricing Tiers (us-east-1 baseline)
- **S3 Standard**: ~$0.023 / GB / month
- **S3 Intelligent-Tiering (Frequent)**: ~$0.023 / GB / month
- **S3 Intelligent-Tiering (Infrequent)**: ~$0.0125 / GB / month
- **S3 Standard-IA**: ~$0.0125 / GB / month (+ $0.01/GB retrieval)
- **S3 Glacier Instant Retrieval**: ~$0.004 / GB / month (+ $0.03/GB retrieval)
- **S3 Glacier Flexible Retrieval**: ~$0.0036 / GB / month
- **S3 Glacier Deep Archive**: ~$0.00099 / GB / month (~$1 per TB/month)

## 10. Interview Questions & Answers

<details>
<summary><strong>Q1: What does Amazon S3 strong read-after-write consistency guarantee?</strong></summary>

**Answer:**
Amazon S3 provides strong read-after-write consistency for `PUT` and `DELETE` requests of objects in all AWS regions:
- Immediately after a successful write of a new object or an overwrite of an existing object, any subsequent read (`GET` or `LIST`) will instantly return the latest mutation.
- This applies to both object data and object metadata.
- Concurrent writes to the exact same key follow a "last-writer-wins" model. If two PUT requests happen simultaneously, the request with the latest timestamp is committed.
</details>

<details>
<summary><strong>Q2: What is the purpose of S3 Bucket Keys when encrypting with AWS KMS?</strong></summary>

**Answer:**
When an object is encrypted with AWS KMS without Bucket Keys, S3 makes a call to the AWS KMS API (`kms:GenerateDataKey` or `kms:Decrypt`) for **every single object upload and download**. In high-throughput data lakes (e.g., querying millions of Parquet files via Athena), this results in millions of KMS API requests, incurring significant cost ($0.03 per 10,000 requests) and risking KMS throttling limits.

Enabling **S3 Bucket Keys** causes S3 to generate an ephemeral bucket-level intermediate data key from KMS. S3 uses this intermediate key to encrypt objects locally within S3 for a short period, reducing direct KMS API calls by up to **99%**.
</details>

<details>
<summary><strong>Q3: How does S3 Block Public Access protect an organization from accidental leaks?</strong></summary>

**Answer:**
S3 Block Public Access acts as a centralized master control switch enforced at either the individual bucket level or across the entire AWS account:
1. **BlockPublicAcls**: Rejects any new public ACLs applied to buckets or objects.
2. **IgnorePublicAcls**: Causes S3 to completely ignore all existing public ACLs.
3. **BlockPublicPolicy**: Rejects any new bucket policy that would grant public access.
4. **RestrictPublicBuckets**: Restricts access to buckets with public policies exclusively to AWS services and authorized account users.
Even if an administrator accidentally writes an `"Effect": "Allow", "Principal": "*"` policy, S3 drops the request if Block Public Access is active.
</details>

<details>
<summary><strong>Q4: When should you choose S3 Intelligent-Tiering over S3 Standard-IA?</strong></summary>

**Answer:**
- Choose **S3 Intelligent-Tiering** when data access patterns are unknown, changing, or unpredictable. It automatically transitions data between frequent and infrequent tiers without charging any data retrieval fees, eliminating financial penalties if archived data is suddenly re-accessed.
- Choose **S3 Standard-IA** only when data access patterns are static, predictable, and infrequent (e.g., monthly compliance reports or disaster recovery backups accessed less than once a quarter), because IA charges a $0.01/GB retrieval fee on every read.
</details>

<details>
<summary><strong>Q5: What is the maximum object size supported by Amazon S3, and how must large files be uploaded?</strong></summary>

**Answer:**
- The maximum size of a single object in Amazon S3 is **5 TB**.
- A single `PUT` request can upload an object up to **5 GB**.
- For objects larger than **100 MB**, AWS best practices mandate using the **S3 Multipart Upload API**. Multipart upload breaks the file into independent parts (from 5 MB to 5 GB each), uploads them in parallel to maximize network throughput, and allows individual failed parts to be retried without restarting the entire upload.
</details>

<details>
<summary><strong>Q6: How do Presigned URLs work under the hood?</strong></summary>

**Answer:**
A presigned URL grants temporary access to an S3 object using cryptographic query parameters:
1. A backend service with valid IAM credentials constructs the S3 URL.
2. It appends AWS Signature Version 4 (SigV4) parameters: the IAM access key ID, timestamp, expiration duration, and a cryptographic HMAC-SHA256 signature generated using the backend's secret key.
3. The client receives the URL and executes a direct HTTP `GET` or `PUT`.
4. S3 validates the cryptographic signature and checks that the URL has not expired. The client accesses the object with the exact permissions of the IAM principal that generated the URL, without requiring AWS credentials or public bucket access.
</details>

<details>
<summary><strong>Q7: What is an S3 Prefix and how does it relate to request throughput?</strong></summary>

**Answer:**
An S3 Prefix is the string between the bucket name and the object name (similar to a folder path, e.g., in `s3://bucket/2026/logs/app.log`, the prefix is `2026/logs/`).
Amazon S3 automatically scales storage partitions behind prefixes. Each unique prefix supports up to **3,500 PUT/POST/DELETE** requests and **5,500 GET/HEAD** requests per second. By partitioning data across 10 distinct prefixes, an application can achieve 35,000 PUTs/sec and 55,000 GETs/sec.
</details>

<details>
<summary><strong>Q8: Why is it critical to configure an `AbortIncompleteMultipartUpload` lifecycle rule?</strong></summary>

**Answer:**
When a multipart upload is initiated, S3 stores each uploaded part as it arrives. If the upload process crashes, loses network connectivity, or is never completed via `CompleteMultipartUpload`, the uploaded parts are not visible as a completed object, but they remain stored in S3 indefinitely.
AWS continues to bill for the storage capacity of these orphaned parts every month. Configuring an `AbortIncompleteMultipartUpload` lifecycle rule instructs S3 to automatically delete abandoned parts after a specified number of days (e.g., 7 days).
</details>
