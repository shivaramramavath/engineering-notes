# EC2: Virtual Servers

EC2 (Elastic Compute Cloud) rents you virtual machines. You pick a CPU/memory shape, an operating system image, and a network location, and a few seconds later you have a Linux or Windows box you control completely. It is the most flexible compute option in AWS and also the one where **you do the most operational work**: patching, scaling, hardening, and recovery are on you.

Reach for EC2 when you need full OS control, long-running processes, unusual software, GPUs or specific hardware, or a lift-and-shift of an existing app. If you only want to run code or containers, [Lambda](./02-lambda.md) and [ECS/Fargate](./03-ecs-fargate.md) usually remove a lot of that work.

---

## The building blocks

```
                    ┌────────────── Instance ──────────────┐
 AMI ─────────────► │  instance type (CPU/RAM/network)     │
 (OS + software)    │  EBS root volume (+ more volumes)    │
                    │  ENI(s) in a subnet, private IP      │
 Security group ──► │  IAM role via instance profile       │
 Key pair/SSM  ───► │  user data (boot script)             │
                    └──────────────────────────────────────┘
```

| Piece | What it is |
|---|---|
| **AMI** | Machine image: the OS and preinstalled software the instance boots from. Region-specific. |
| **Instance type** | Hardware shape, e.g. `t3.micro`, `m7g.large`. |
| **EBS volume** | Network-attached block storage (the "disk"). Survives stop/start. |
| **Instance store** | Disk physically on the host on some types. **Lost** on stop/terminate. Good for scratch data only. |
| **Security group** | Stateful virtual firewall around the instance's network interface. |
| **Key pair / SSM** | How you get a shell. Prefer SSM Session Manager (below). |
| **User data** | Script run at first boot to configure the instance. |
| **Instance profile** | Wrapper that attaches an [IAM role](../01-foundations/03-iam.md) to the instance. |

## Instance types

The name encodes the shape: `m7g.xlarge` → family `m`, generation `7`, attribute `g` (Graviton / ARM), size `xlarge`.

| Family | Optimised for | Typical use |
|---|---|---|
| `t` | Burstable general purpose | Small apps, dev boxes |
| `m` | Balanced general purpose | App servers, most things |
| `c` | Compute | Batch, encoding, high-CPU APIs |
| `r` / `x` | Memory | Caches, in-memory DBs |
| `i` / `d` | Local storage | Databases needing fast local disk |
| `g` / `p` | GPU | ML, graphics |

Things to know:

- **Burstable (`t`) instances** earn CPU credits while idle and spend them under load. Sustained high CPU can exhaust credits and throttle you (or cost extra in "unlimited" mode). They suit spiky, low-average workloads, not steady 80% CPU.
- **Graviton (ARM, the `g` suffix)** instances are usually cheaper for the same performance, but your software and Docker images must be built for `arm64`.
- Newer generations are generally better value than older ones. Check the current list in the console or `aws ec2 describe-instance-types` instead of trusting a tutorial.

## Launching an instance

Console is fine to explore. The CLI shows what's actually being decided:

```bash
aws ec2 run-instances \
  --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
  --instance-type t3.micro \
  --subnet-id subnet-0abc1234 \
  --security-group-ids sg-0abc1234 \
  --iam-instance-profile Name=my-instance-profile \
  --metadata-options HttpTokens=required \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=demo}]' \
  --user-data file://boot.sh
```

- The `resolve:ssm:` form fetches the **current** Amazon Linux 2023 AMI for the region, so you don't hardcode region-specific AMI IDs that go stale.
- `HttpTokens=required` enforces **IMDSv2** (see security below).
- A subnet and security group come from your [VPC](../04-networking/01-vpc.md). New accounts have a default VPC that makes quick experiments easy; production setups use their own.

User data runs once, as root, at first boot:

```bash
#!/bin/bash
dnf install -y nginx
systemctl enable --now nginx
```

If your user data "didn't work", read `/var/log/cloud-init-output.log` on the instance.

## Lifecycle and what each state costs

```
pending → running ⇄ stopping → stopped → (start) → pending → running
                │                  │
                └─► shutting-down ─┴─► terminated  (gone for good)
```

| Action | Compute billed? | Disk (EBS) billed? | Notes |
|---|---|---|---|
| **Running** | Yes | Yes | |
| **Stop** | No | **Yes** | Keeps EBS data. Public IP changes unless you use an Elastic IP. May move to new hardware on start. |
| **Terminate** | No | Root volume deleted by default (data volumes depend on their delete-on-termination flag) | Irreversible. |
| **Hibernate** | No | Yes | Saves RAM to disk, on supported types. |

Common misconception: "I stopped it, so it's free." Compute stops billing, but the EBS volumes, snapshots and Elastic IPs keep billing.

## Networking and access

- **Security groups** are **stateful allow-lists**: you only add allow rules, and return traffic is automatically permitted. No deny rules. Default: all inbound blocked, all outbound allowed.
  ```bash
  # Allow HTTPS from anywhere
  aws ec2 authorize-security-group-ingress --group-id sg-0abc1234 \
    --protocol tcp --port 443 --cidr 0.0.0.0/0
  ```
  A security group can reference **another security group** as a source (e.g. DB allows port 5432 only from the app's SG), which is the idiomatic way to wire tiers together.
- **Public IP vs Elastic IP**: an auto-assigned public IP changes on stop/start. An Elastic IP is a static address you own. Public IPv4 addresses are billed, so don't hand them out freely. Instances behind a load balancer often need none.
- **Getting a shell:** prefer **SSM Session Manager**: no open port 22, no key management, access controlled by IAM and logged. It needs the SSM agent (preinstalled on Amazon Linux), an instance role with the `AmazonSSMManagedInstanceCore` policy, and a network path to the SSM endpoints.
  ```bash
  aws ssm start-session --target i-0123456789abcdef0
  ```
  (Requires the Session Manager plugin for the CLI.) Classic SSH with a key pair still works, but restrict port 22 to your IP, never `0.0.0.0/0`.

## Storage on EC2

- **EBS** is network block storage, replicated within an AZ, and attached to one instance at a time (multi-attach exists for specific volume types). Volumes live in a **single AZ**, so to move data across AZs you snapshot and restore.
- Volume types: `gp3` is the sensible general-purpose default (IOPS and throughput are configurable independently of size); `io2` for demanding databases; `st1`/`sc1` for throughput/cold workloads.
- **Snapshots** are incremental backups stored in S3-backed storage; use them for backups and to build AMIs.
- For shared file storage across instances, look at **EFS**; for objects, [S3](../03-storage-and-databases/01-s3.md).

## Paying for EC2

| Option | How it works | Use for |
|---|---|---|
| **On-Demand** | Pay per second (Linux) with no commitment | Spiky, unknown, short-lived |
| **Savings Plans / Reserved** | Commit to usage for 1 or 3 years for a discount | Steady baseline load |
| **Spot** | Spare capacity at a steep discount, but AWS can reclaim it with short notice | Fault-tolerant batch, CI, stateless workers |

Start On-Demand, measure, then commit to a Savings Plan for the stable baseline. Right-size first: committing to oversized instances locks in waste.

## Production considerations

- **Don't run one precious server.** Put instances in an **Auto Scaling group** across multiple AZs behind a [load balancer](../04-networking/03-load-balancing-and-api-gateway.md). Treat instances as disposable: bake config into AMIs or user data, keep state in RDS/S3/DynamoDB.
- **Enforce IMDSv2.** The instance metadata service (`169.254.169.254`) hands out the role's temporary credentials. IMDSv1 is vulnerable to SSRF-style credential theft, since a simple GET request can read it. IMDSv2 requires a session token. Set `HttpTokens=required` on new instances. (Amazon Linux 2023 defaults to IMDSv2.)
- **Least-privilege instance roles.** Anything on the box that can reach the metadata service can use the role.
- **Patching is yours.** Use Systems Manager Patch Manager, or rebuild and roll AMIs regularly.
- **Tag everything** (`Name`, `env`, `owner`) so cost and cleanup are tractable.
- **Monitoring:** CloudWatch gives CPU, network and disk-ops by default, but **not memory or disk usage**. Install the CloudWatch agent for those. See [Observability](../06-operations/04-observability.md).

## Common mistakes

- Opening SSH (22) or database ports to `0.0.0.0/0`.
- Putting state only on the instance store or root disk of a single instance, then losing it.
- Forgetting that stop ≠ free (EBS, Elastic IPs).
- Looking in the wrong **region** and thinking the instance is gone.
- Hardcoding AMI IDs: they're region-specific and age. Use the SSM parameter or build your own.
- Using `t` instances for sustained high CPU, then wondering why performance collapses.
- Building an `x86` Docker image and deploying to a Graviton instance (or vice versa).

## Debugging

| Symptom | Check |
|---|---|
| Can't SSH / connect | Security group inbound rule, **subnet route to an internet gateway** and public IP (for internet access), NACLs, correct key/user (`ec2-user` on Amazon Linux) |
| Instance fails status checks | **System** check failure = AWS host problem (stop/start to migrate); **instance** check failure = OS-level (console screenshot, `get-console-output`) |
| App unreachable but SSH works | App listening on `0.0.0.0` not `127.0.0.1`; security group port |
| User data didn't run | `/var/log/cloud-init-output.log`; script needs a shebang; it runs only at first boot by default |
| Can't reach the internet from private subnet | No NAT Gateway / route (see [VPC](../04-networking/01-vpc.md)) |
| `UnauthorizedOperation` | IAM permissions (see [IAM](../01-foundations/03-iam.md)); `--dry-run` is handy to test |
| "Insufficient instance capacity" | Try a different instance type or AZ |

```bash
aws ec2 describe-instance-status --instance-ids i-0123456789abcdef0 --include-all-instances
aws ec2 get-console-output --instance-id i-0123456789abcdef0 --output text
```

## Quick Summary

- EC2 = VMs you fully control and fully operate. Choose it for control; choose Lambda/Fargate to do less ops.
- Core pieces: **AMI, instance type, EBS, security group, IAM role (instance profile), user data.**
- **Stop** halts compute billing but not EBS/Elastic IP; **terminate** is permanent.
- Use **SSM Session Manager**, **IMDSv2**, least-privilege roles, and tight security groups.
- Design for disposability: ASG across AZs behind a load balancer, state elsewhere.
- Pay On-Demand first, then Savings Plans for the baseline; Spot for fault-tolerant work.
