## 1. What & Why

Amazon Elastic Compute Cloud (Amazon EC2) provides scalable, resizable compute capacity in the cloud. It represents the foundational Infrastructure-as-a-Service (IaaS) offering of AWS, giving engineers complete administrative control over virtual server instances, operating system kernels, storage volumes, network interfaces, and security configurations.

While modern serverless and container platforms abstract away infrastructure management, EC2 remains the architectural backbone for:
- Statefull workloads (databases, legacy ERP systems, file servers).
- High-Performance Computing (HPC), machine learning training, and GPU rendering.
- Kubernetes worker node fleets (Amazon EKS or self-managed).
- Workloads requiring custom Linux kernel parameters, device drivers, or specific hypervisor-level CPU flags.

Understanding EC2 architecture—including the AWS Nitro System, virtualization types, metadata retrieval (IMDSv2), instance storage types, and lifecycle behavior—is required knowledge for designing resilient, cost-efficient, and secure cloud topologies.

## 2. Core Concepts

### 2.1 The AWS Nitro System
Modern EC2 instances (5th generation and later: `c5`, `m5`, `r5`, `t4g`, `c7g`, etc.) are powered by the **AWS Nitro System**, replacing legacy Xen virtualization.
- **Nitro Cards**: Dedicated hardware PCI cards offloading VPC networking (Enhanced Networking with ENA), EBS storage IOPS, and local NVMe management.
- **Nitro Security Chip**: Hardware root-of-trust integrated into the motherboard; continuously traps and authorizes system firmware updates.
- **Nitro Hypervisor**: A lightweight, stripped-down Kernel-based Virtual Machine (KVM) core providing near bare-metal performance, memory isolation, and virtually zero hypervisor CPU overhead.

### 2.2 Instance Naming & Family Taxonomy
EC2 instance types follow a structured naming convention:
```
         c   7   g   n   .  2xlarge
         |   |   |   |        |
    Family  Gen  |  Capabilities  Size
                 Processor (g = Graviton ARM)
```
- **Primary Families**:
  - `General Purpose (T, M)`: Balanced compute, memory, and networking. Bursting capabilities (`T3/T4g`) with CPU credits.
  - `Compute Optimized (C)`: High compute-to-memory ratio (2 GB RAM per vCPU). Ideal for batch processing, web servers, video encoding.
  - `Memory Optimized (R, X, z)`: High memory-to-compute ratio (8–32 GB RAM per vCPU). In-memory caches (Redis), relational databases, real-time analytics.
  - `Accelerated Computing (P, G, Inf, Trn)`: Hardware GPU (NVIDIA Tensor Core), Trainium, or Inferentia accelerators for LLM training and graphics.
  - `Storage Optimized (I, D, H)`: Direct-attached NVMe SSDs delivering tens of thousands of low-latency IOPS for distributed NoSQL databases.
- **Suffix Modifiers**:
  - `a`: AMD EPYC processors.
  - `g`: AWS Graviton ARM-based processors (up to 40% better price-performance).
  - `i`: Intel Xeon Scalable processors.
  - `n`: High network bandwidth (up to 100/200 Gbps).
  - `d`: Attached local NVMe SSD instance storage.

### 2.3 Storage Architecture: EBS vs. Instance Store
- **Amazon Elastic Block Store (EBS)**: Network-attached virtual block storage volume. Independent lifecycle from the EC2 instance; persists data across instance stop/start cycles. Replicated within an Availability Zone.
- **Instance Store (Ephemeral Storage)**: Physical NVMe/SATA SSDs located directly in the physical host rack. Delivers microsecond latency and extreme IOPS, but is **ephemeral**: data is lost permanently when the instance stops, terminates, or undergoes underlying host hardware replacement.

### 2.4 Instance Metadata Service (IMDSv2 vs IMDSv1)
The Instance Metadata Service (`169.254.169.254`) allows software running inside the instance to query instance ID, IP addresses, IAM role security tokens, and user data.
- **IMDSv1 (Deprecated/Insecure)**: Request/Response model via simple HTTP GET requests. Highly susceptible to Server-Side Request Forgery (SSRF) and open reverse-proxy exploitation.
- **IMDSv2 (Mandatory Modern Standard)**: Session-oriented protocol. Requires a `PUT` request with a `X-aws-ec2-metadata-token-ttl-seconds` header to obtain a cryptographic session token before executing `GET` queries. Bounded by a packet hop-limit (default 1), preventing SSRF tokens from traversing container or proxy boundaries.

## 4. Syntax & Usage

### 4.1 Launching an EC2 Instance with IMDSv2 via AWS CLI
```bash
aws ec2 run-instances \
  --image-id ami-0c7217cdde317cfec \
  --instance-type t4g.medium \
  --key-name production-bastion-key \
  --subnet-id subnet-0123456789abcdef0 \
  --security-group-ids sg-0feeedcba98765432 \
  --iam-instance-profile Name=WebServerEC2RoleProfile \
  --metadata-options "HttpEndpoint=enabled,HttpTokens=required,HttpPutResponseHopLimit=1" \
  --block-device-mappings '[
    {
      "DeviceName": "/dev/xvda",
      "Ebs": {
        "VolumeSize": 30,
        "VolumeType": "gp3",
        "Iops": 3000,
        "Throughput": 125,
        "Encrypted": true,
        "DeleteOnTermination": true
      }
    }
  ]' \
  --user-data file://bootstrap.sh \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=web-app-01},{Key=Environment,Value=production}]'
```

### 4.2 Querying IMDSv2 Inside an Instance
```bash
# Step 1: Request a 6-hour cryptographic session token (PUT)
TOKEN=$(curl -s -S -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Step 2: Use the token in the header of subsequent GET queries
INSTANCE_ID=$(curl -s -S -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id)

AVAILABILITY_ZONE=$(curl -s -S -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/availability-zone)

IAM_ROLE=$(curl -s -S -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/)

echo "Instance $INSTANCE_ID running in $AVAILABILITY_ZONE with role $IAM_ROLE"
```

```bash

  --instance-ids i-0abcdef1234567890 \
  --query "Reservations[0].Instances[0].BlockDeviceMappings[0].Ebs.VolumeId" \

# 2. Modify volume from 50GB to 100GB with increased throughput

  --volume-id $VOLUME_ID \
  --size 100 \
  --volume-type gp3 \

aws ec2 describe-volumes-modifications \
  --volume-ids $VOLUME_ID \
  --query "VolumesModifications[0].ModificationState" \

# sudo xfs_growfs -d /
# For EXT4:
```

## 6. Best Practices

1. **Mandate IMDSv2 via SCP**: Apply an AWS Organizations SCP preventing any `RunInstances` API call that omits `"ec2:MetadataHttpTokens": "required"`.
2. **Never Open Port 22 to `0.0.0.0/0`**: Eliminate SSH keys entirely. Attach `AmazonSSMManagedInstanceCore` to the IAM instance profile and connect via **AWS SSM Session Manager**.
3. **Prefer Graviton Instances (`g` suffix)**: Adopt AWS Graviton3/Graviton4 (`c7g`, `m7g`, `r7g`) instances over Intel/AMD for up to 40% improved price-to-performance on Linux workloads.
4. **Tune GP3 Volume Baselines**: Use `gp3` instead of legacy `gp2`. `gp3` provides a baseline of 3,000 IOPS and 125 MB/s throughput included at zero extra cost, detached from storage volume gigabytes.
5. **Separate Root Volumes from Data Volumes**: Keep the OS kernel and packages on `/dev/xvda`. Mount application databases, cache stores, or large uploads on a secondary EBS volume (`/dev/sdb`) to enable volume snapshots without stopping the OS.

## 7. Common Mistakes

| Mistake | Consequence | Correct Pattern |
|:---|:---|:---|
| **Using IMDSv1 in Production** | Applications vulnerable to SSRF can leak IAM instance profile temporary credentials. | Enforce `HttpTokens=required` and `HttpPutResponseHopLimit=1` on all launch templates. |
| **Storing Persistent Data on Instance Store** | Complete data loss occurs whenever the EC2 instance is stopped or underlying hardware fails. | Restrict Instance Store to temporary buffers, swap space, or distributed multi-node replicas. Use EBS for persistence. |
| **Using Public Subnets for Backend EC2** | Direct exposure to internet scanning, DDoS attacks, and automated vulnerability exploitation. | Place EC2 instances in private subnets with no public IPs; route egress via NAT Gateway and ingress via ALB. |
| **Over-Allocating GP2 Volumes for IOPS** | Inflating disk sizes to hundreds of gigabytes just to attain IOPS burst credits on legacy gp2. | Migrate to `gp3` where IOPS and throughput are independently provisioned without increasing disk size. |
| **Baking Credentials into Custom AMIs** | Leaking private API keys, hardcoded passwords, or static IAM credentials across cloned servers. | Use IAM Instance Profiles for AWS permissions and AWS Secrets Manager for third-party application credentials. |
| **Forgetting CloudWatch Agent for Memory** | Default CloudWatch EC2 metrics only capture hypervisor-level metrics (CPU, Network, Disk Read/Write). Memory exhaustion goes unnoticed. | Install and configure the unified CloudWatch Agent inside the OS to emit `mem_used_percent`. |

## 8. Performance, Security & Cost Notes

### Hypervisor Performance Isolation
- **CPU Burstable Performance (`T` instances)**: Accumulate CPU credits while idle. If a `t3` or `t4g` instance runs continuously at 100% CPU in `unlimited` mode, AWS bills an extra $0.05 per vCPU-hour. For sustained production loads, choose fixed-performance `M` or `C` instances.
- **Enhanced Networking**: Powered by the Elastic Network Adapter (ENA). Always verify the ENA kernel module is loaded (`modinfo ena`) to achieve sub-millisecond inter-instance latency and up to 100 Gbps network interfaces.

### Security Hardening
- **EBS Encryption by Default**: Enable account-level default EBS encryption in the EC2 console. Ensures every snapshot and root volume is encrypted with KMS without relying on engineer discipline.
- **Instance Isolation**: AWS Nitro Hypervisor does not expose an interactive host OS to AWS staff or hypervisor administrators. There is no physical memory dumping or host shell access.

### Cost Optimization Strategies
- **Spot Instances**: Use for stateless, fault-tolerant background workers (up to 90% discount).
- **Compute Savings Plans**: Commit to 1- or 3-year hourly spend for flexible discounts across EC2, Fargate, and Lambda.
- **Stop Idle Dev Instances**: Automate night and weekend shutdowns using AWS Instance Scheduler or EventBridge rules.

## 10. Interview Questions & Answers

<details>
<summary><strong>Q1: What is the architectural purpose of the AWS Nitro System?</strong></summary>

**Answer:**
The AWS Nitro System is a hardware and software virtualization platform. In legacy virtualization (Xen), the hypervisor on the physical host handled CPU/memory isolation, network packet routing, storage encapsulation, and management APIs, consuming up to 15–20% of host resources.

Nitro offloads network (VPC/ENA), storage (EBS/NVMe), and system control functions onto dedicated PCIe hardware cards (Nitro Cards). The remaining physical host runs a tiny, stripped-down Nitro Hypervisor that only handles CPU and memory allocation. This provides near 100% host resource allocation to customer VMs, consistent low latency, and enhanced physical security via the Nitro Security Chip.
</details>

<details>
<summary><strong>Q2: How does IMDSv2 mitigate Server-Side Request Forgery (SSRF) vulnerabilities?</strong></summary>

**Answer:**
Under IMDSv1, any attacker who exploited an SSRF vulnerability in a web app could force the server to send an HTTP GET request to `http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>`, immediately exposing the instance's STS temporary tokens.

IMDSv2 enforces two critical protections:
1. **Session Token Requirement**: Callers must first send a `PUT` request with an `X-aws-ec2-metadata-token-ttl-seconds` header. Many basic SSRF attack vectors (e.g., standard image-rendering or URL-fetching exploits) cannot construct arbitrary HTTP methods or custom headers.
2. **Hop-Limit Enforcement**: The `HttpPutResponseHopLimit` is configured to `1` by default. Network packets attempting to traverse an intermediate proxy, reverse proxy, or container bridge increment the IP TTL hop counter, causing the packet to be dropped by the network stack before reaching IMDS.
</details>

<details>
<summary><strong>Q3: What happens to data stored on an EC2 Instance Store volume during a Stop/Start cycle?</strong></summary>

**Answer:**
Data on an Instance Store volume is **permanently lost**. 

Instance Store drives are physical solid-state drives directly attached to the host hardware chassis. When an instance enters the `stopped` state, AWS releases the physical host lease and deallocates the hardware. When restarted, the instance launches on a completely different physical server with fresh, wiped disks. In contrast, EBS volumes are network-attached block devices and preserve all data across stop/start operations.
</details>

<details>
<summary><strong>Q4: How do EBS GP2 and GP3 volume performance characteristics differ?</strong></summary>

**Answer:**
- **gp2 (Legacy)**: Baseline IOPS was strictly coupled to volume size (3 IOPS per GB, minimum 100, maximum 16,000). Volumes under 1 TB relied on an unpredictable I/O credit burst bucket. Throughput was capped at 250 MB/s.
- **gp3 (Modern)**: IOPS and throughput are completely decoupled from volume storage capacity. Every gp3 volume provides a free baseline of **3,000 IOPS** and **125 MB/s** throughput regardless of volume size, and costs 20% less per GB than gp2. Higher IOPS (up to 16,000) and throughput (up to 1,000 MB/s) can be provisioned independently without buying unneeded disk space.
</details>

<details>
<summary><strong>Q5: Can you change an EC2 instance type without terminating the virtual machine?</strong></summary>

**Answer:**
Yes, for EBS-backed instances:
1. Stop the instance (`aws ec2 stop-instances`).
2. Modify the instance type attribute (`aws ec2 modify-instance-attribute --instance-id <ID> --instance-type <NewType>`).
3. Start the instance (`aws ec2 start-instances`).

*Note*: The new instance type must be compatible with the AMI architecture (e.g., cannot switch directly from x86 to ARM/Graviton without an OS/AMI reinstall), virtualization type (HVM), and network configuration (ENA support).
</details>

<details>
<summary><strong>Q6: How does AWS Systems Manager Session Manager eliminate the need for SSH keys and bastion hosts?</strong></summary>

**Answer:**
Session Manager communicates over an outbound HTTPS (port 443) connection maintained by the `amazon-ssm-agent` running inside the guest OS to the Systems Manager service endpoint.
- No inbound ports (like TCP 22) need to be open in the Security Group.
- No public IPv4 address or Internet Gateway is required (works in fully private subnets via VPC Endpoints).
- Authentication and authorization are governed via AWS IAM rather than static SSH key pairs.
- Every session command and keystroke can be audited, encrypted, and streamed to AWS CloudTrail and Amazon CloudWatch Logs.
</details>

<details>
<summary><strong>Q7: What is the difference between an EBS Snapshot and an AMI?</strong></summary>

**Answer:**
- **EBS Snapshot**: A point-in-time, incremental block-level backup of a single EBS volume stored in Amazon S3. Only modified disk blocks are copied in subsequent snapshots.
- **Amazon Machine Image (AMI)**: A comprehensive machine template that packages:
  1. A root volume template (which is backed by an EBS snapshot).
  2. Block device mappings defining secondary volumes or instance stores.
  3. Launch permissions (who can launch instances from this AMI).
  4. Architectural metadata (architecture type: x86_64 vs arm64, kernel ID, virtualization type).
</details>

<details>
<summary><strong>Q8: What is an EC2 Placement Group and what are its three strategies?</strong></summary>

**Answer:**
Placement groups influence where EC2 instances are physically positioned within an Availability Zone's hardware racks:
1. **Cluster**: Packs instances physically close together on the same rack or low-latency network switch. Delivers maximum network throughput and minimum latency (HPC, distributed MPI). Higher blast radius if rack hardware fails.
2. **Spread**: Places each instance on completely distinct physical hardware racks, power supplies, and network switches (max 7 instances per AZ). Maximizes fault tolerance for critical nodes.
3. **Partition**: Divides the placement group into logical partitions; instances in one partition do not share hardware with other partitions. Ideal for distributed data systems like Kafka, Cassandra, and HDFS.
</details>
