## What & Why

In production Linux systems, reliable connectivity hinges on two core components:
1. **Network Interfaces**: Software or physical representations of network links (physical Ethernet, loopback, VLAN 802.1Q tags, virtual bridges, WireGuard tunnels, and container `veth` pairs).
2. **Routing Subsystem**: The kernel engine that inspects the destination IP address of every egress or forwarded packet and looks up the Forwarding Information Base (FIB) to determine the next-hop gateway and egress interface.

While runtime commands like `ip route` and `ip addr` alter the live kernel state immediately, persistent network configuration differs across modern distributions:
- **Ubuntu (20.04+)**: Utilizes **Netplan**, a declarative YAML configuration abstraction engine that generates backend renderer configurations for `systemd-networkd` or `NetworkManager`.
- **RHEL 9 / Rocky Linux 9**: Relies on **NetworkManager** via the `nmcli` command-line utility and keyfile format under `/etc/NetworkManager/system-connections/`.

Understanding both live kernel manipulation (`iproute2`) and persistent configuration frameworks is critical for configuring multi-homed servers, policy-based routing (PBR), and cloud VPC network attachments.

## Core Concepts

### Network Interface Naming Conventions (Predictable Interface Names)
Modern Linux systems drop legacy names like `eth0` and `wlan0` in favor of predictable names generated by `udev` (systemd scheme):
- `enp3s0`: Ethernet (`en`), PCI bus (`p3`), slot (`s0`).
- `ens33`: Ethernet on hotplug slot 33.
- `eno1`: Embedded / on-board Ethernet device 1.
- `lo`: Loopback interface (`127.0.0.1/8`, `::1/128`).
- `veth*`: Virtual Ethernet pair used to bridge container network namespaces into the host bridge.

### IPv4 Subnetting and CIDR Notation
Classless Inter-Domain Routing (CIDR) denotes network prefix length via `/N`:
$$\text{Netmask bits} = N, \quad \text{Host bits} = 32 - N, \quad \text{Usable Hosts} = 2^{(32 - N)} - 2$$
*(Minus 2 accounts for Network Address and Broadcast Address).*

| CIDR Prefix | Subnet Mask | Usable IPv4 Host Addresses | Common Production Context |
| :--- | :--- | :--- | :--- |
| `/24` | `255.255.255.0` | 254 | Standard subnet / Private VPC segment |
| `/28` | `255.255.255.240`| 14 | Small cluster / Database subnet |
| `/30` | `255.255.255.252`| 2 | Point-to-point router link |
| `/32` | `255.255.255.255`| 1 (Host route) | Loopback / Single host route |

### The Kernel Routing Table (FIB)
When a packet needs transmission:
1. The kernel performs a **longest prefix match** on the destination IP address against the routing table.
2. If multiple routes match, the more specific route (larger CIDR number, e.g. `/24` over `/16`) takes precedence.
3. If prefix lengths are identical, the route with the lowest **metric** (cost) is chosen.
4. If no specific route matches, the packet falls back to the **Default Gateway** (`default via <gateway_ip> dev <interface>`).

### Policy-Based Routing (PBR) and Multiple Routing Tables
Standard routing makes decisions based **only on the destination IP address**. 
Policy-Based Routing (PBR) enables routing decisions based on:
- Source IP address (essential for multi-homed servers with dual NICs).
- Firewall mark (fwmark) set by `nftables`.
- Egress protocol or port.
Managed using `ip rule` and custom routing tables defined in `/etc/iproute2/rt_tables`.

## Internal Working

```
                                  Outbound Packet Generated
                                              |
                                              v
+-----------------------------------------------------------------------------------------+
|                                    Routing Policy Database                              |
|                                       (ip rule list)                                    |
|   Rule 0:     from all lookup local                                                     |
|   Rule 100:   from 192.168.10.50 lookup table_isp2  <--- Policy Match                   |
|   Rule 32766: from all lookup main                  <--- Standard Default               |
|   Rule 32767: from all lookup default                                                   |
+---------------------------------------------+-------------------------------------------+
                                              |
                       +----------------------+----------------------+
                       | Matches Rule 100                            | Falls through to Rule 32766
                       v                                             v
+---------------------------------------------+ +-----------------------------------------+
|        Custom Table (table_isp2)            | |              Main Table                 |
|   default via 192.168.10.1 dev enp3s0       | |   10.0.0.0/24 dev enp1s0 proto kernel   |
|                                             | |   default via 10.0.0.1 dev enp1s0       |
+----------------------+----------------------+ +--------------------+--------------------+
                       |                                             |
                       +----------------------+----------------------+
                                              |
                                              v
+-----------------------------------------------------------------------------------------+
|                                 Longest Prefix Match (LPM)                              |
|                Selects Next-Hop IP and Egress Network Interface (`net_device`)          |
+---------------------------------------------+-------------------------------------------+
                                              |
                                              v
+-----------------------------------------------------------------------------------------+
|                                  ARP / Neighbor Table Lookup                            |
|             Maps Next-Hop IP -> MAC Address (via `ip neigh` cache or ARP Request)        |
+---------------------------------------------+-------------------------------------------+
                                              |
                                              v
                                Transmit Frame onto Wire / veth
```

### Route Selection Sequence
1. Kernel evaluates rules in the **Routing Policy Database (RPDB)** sequentially in ascending priority order (`0` to `32767`).
2. When a rule matches, the kernel consults that rule's designated routing table.
3. The routing engine searches the table for the most specific route matching the destination IP.
4. If a route is found, the lookup terminates. If no route matches in that table, the engine continues to the next rule in the RPDB.

## Syntax & CLI Tools

### Managing Interfaces with `ip link`
```bash
# Display link status and MAC addresses
ip link show

# Bring an interface up or down
sudo ip link set dev enp3s0 up
sudo ip link set dev enp3s0 down

# Change interface MTU
sudo ip link set dev enp3s0 mtu 9000

# Rename an interface (interface must be down first)
sudo ip link set dev enp3s0 name eth-internal
```

### Managing IP Addresses with `ip address`
```bash
# Display all assigned addresses with subnet masks
ip -4 addr show

# Add an IP address to an interface (runtime, non-persistent)
sudo ip addr add 192.168.1.100/24 dev enp3s0

# Remove an IP address
sudo ip addr del 192.168.1.100/24 dev enp3s0

# Add a secondary IP alias
sudo ip addr add 10.0.0.5/32 dev enp3s0 label enp3s0:vip
```

### Managing Routes with `ip route`
```bash
# Show main routing table
ip route show

# Add a static route to a subnet
sudo ip route add 10.200.0.0/16 via 192.168.1.1 dev enp3s0

# Add a default gateway
sudo ip route add default via 192.168.1.1 dev enp3s0

# Delete a route
sudo ip route del 10.200.0.0/16

# Check which route and interface the kernel will pick for a specific IP
ip route get 8.8.8.8
```

### Policy Routing with `ip rule`
```bash
# List all active routing rules
ip rule show

# Route all traffic originating from a specific source IP through table 100
sudo ip rule add from 192.168.20.50 table 100 priority 500

# Add default route inside table 100
sudo ip route add default via 192.168.20.1 dev enp4s0 table 100
```

## Progressive Practical Examples

### Example 1: Declarative Netplan Configuration on Ubuntu 24.04
Configure static IP, gateway, and DNS servers persistently.

```yaml
# /etc/netplan/01-netcfg.yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    enp3s0:
      dhcp4: no
      addresses:
        - 192.168.1.50/24
      routes:
        - to: default
          via: 192.168.1.1
          metric: 100
      nameservers:
        addresses:
          - 1.1.1.1
          - 8.8.8.8
        search:
          - corp.internal
```

```bash
# Test configuration with safety fallback (auto-reverts in 120s if you lose connection)
sudo netplan try

# Apply permanently
sudo netplan apply
```

### Example 2: Declarative Network Configuration on RHEL 9 / Rocky Linux via `nmcli`
Configure a static connection on Enterprise Linux without touching raw files.

```bash
# 1. Create a new static Ethernet connection profile
sudo nmcli con add type ethernet con-name "prod-lan" ifname enp3s0 \
  ip4 192.168.1.50/24 gw4 192.168.1.1

# 2. Configure DNS servers and search domains
sudo nmcli con mod "prod-lan" ipv4.dns "1.1.1.1 8.8.8.8"
sudo nmcli con mod "prod-lan" ipv4.dns-search "corp.internal"
sudo nmcli con mod "prod-lan" ipv4.method manual

# 3. Bring the connection up
sudo nmcli con up "prod-lan"

# 4. Verify persistent profile on disk
ls -l /etc/NetworkManager/system-connections/prod-lan.nmconnection
```

### Example 3: Multi-Homed Dual-NIC Routing (Preventing Asymmetric Drops)
**Scenario**: A server has two NICs connected to two different subnets (`192.168.1.0/24` and `10.0.0.0/24`), each with its own gateway to the internet. Traffic entering `10.0.0.50` tries to reply via the default gateway on `192.168.1.1`, causing dropped packets due to Reverse Path Filtering.

```bash
#!/usr/bin/env bash
set -euo pipefail

# 1. Define custom routing table name in /etc/iproute2/rt_tables if absent
if ! grep -q "200 table_secondary" /etc/iproute2/rt_tables; then
    echo "200 table_secondary" | sudo tee -a /etc/iproute2/rt_tables
fi

# 2. Add routing rule: if packet originates from the secondary NIC IP, use secondary table
sudo ip rule add from 10.0.0.50 table table_secondary priority 200

# 3. Add default route inside the secondary routing table
sudo ip route add default via 10.0.0.1 dev enp4s0 table table_secondary

# 4. Add local subnet route inside the secondary table
sudo ip route add 10.0.0.0/24 dev enp4s0 proto kernel scope link src 10.0.0.50 table table_secondary

# 5. Verify rule and route lookup
ip rule show
ip route show table table_secondary
ip route get 8.8.8.8 from 10.0.0.50
```

### Example 4: Creating a Linux Bridge and Attaching Interfaces
Virtual bridges act as software Layer 2 Ethernet switches, essential for virtualization (KVM) and containers.

```bash
# 1. Create software bridge
sudo ip link add name br0 type bridge

# 2. Assign IP to the bridge itself
sudo ip addr add 192.168.100.1/24 dev br0

# 3. Attach a physical interface or veth to the bridge
sudo ip link set dev enp5s0 master br0

# 4. Bring up the bridge
sudo ip link set dev br0 up
sudo ip link set dev enp5s0 up

# 5. Inspect bridge ports and MAC learning table
ip link show master br0
bridge fdb show dev br0
```

### Example 5: Persistent Policy Routing in Netplan
How to configure the dual-NIC policy routing from Example 3 persistently in Ubuntu Netplan:

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    enp3s0: # Primary interface
      addresses:
        - 192.168.1.50/24
      routes:
        - to: default
          via: 192.168.1.1
    enp4s0: # Secondary interface with PBR
      addresses:
        - 10.0.0.50/24
      routes:
        - to: default
          via: 10.0.0.1
          table: 200
      routing-policy:
        - from: 10.0.0.50
          table: 200
```

## Best Practices

1. **Always Use `netplan try` When Editing Remote Netplan Configurations**: Never run `netplan apply` blindly over an active SSH session. `netplan try` applies changes temporarily with a countdown timer. If you lose network connectivity and cannot confirm with `Enter`, it reverts to the last known working state automatically.
2. **Never Configure Two Default Gateways in the Same Routing Table**: Having two default gateways without metrics or policy tables causes unpredictable route flapping and broken TCP connections. If dual uplinks are required, use policy routing tables or set explicit metrics (`metric 100` vs `metric 200`).
3. **Use Predictable Interface Names in Infrastructure Automation**: Avoid hardcoding `eth0` in Ansible or cloud-init templates. Query the active default interface dynamically: `ip route show default | awk '{print $5}'`.
4. **Use Subnet Calculator Tools to Validate CIDR Boundaries**: Validate subnet sizes, broadcast addresses, and host ranges with `ipcalc <ip>/<cidr>` before provisioning network subnets in cloud infrastructure.
5. **Manage MTU Mismatches in Cloud & Tunnel Interfaces**: When setting up WireGuard, IPsec, or VXLAN tunnels, decrease interface MTU to account for encapsulation headers (e.g., set WireGuard MTU to `1420` on standard 1500-byte links).
6. **Set Explicit `proto kernel` and `scope` When Scripting Routes**: When manipulating routes programmatically, ensure local link routes define `scope link` so the kernel understands they do not require an upstream gateway.

## Common Mistakes & Gotchas

| Mistake | Why It Fails | Correct Pattern |
| :--- | :--- | :--- |
| Adding two default gateways via `ip route add default ...` | Causes route conflict or unpredictable outbound gateway flapping. | Use different metrics or separate routing tables via `ip rule`. |
| Running `ip route add` or `ip addr add` expecting persistence across reboot | `ip` commands modify kernel RAM data structures; all changes vanish upon reboot. | Persist via Netplan (`/etc/netplan/*.yaml`) or NetworkManager (`nmcli`). |
| Editing `/etc/network/interfaces` on modern Ubuntu | Modern Ubuntu ignores `ifupdown` by default; Netplan is the active network management layer. | Edit `/etc/netplan/*.yaml` and execute `netplan apply`. |
| Indentation errors in Netplan YAML files | YAML is whitespace-sensitive; tabs or uneven spaces cause `netplan apply` syntax parse errors. | Use 2-space indentation and test with `netplan generate`. |
| Missing reverse path rule when pinging secondary NIC from external network | Strict reverse path filtering (`rp_filter = 1`) drops replies whose source interface does not match ingress. | Configure policy routing or adjust `sysctl net.ipv4.conf.all.rp_filter = 2` (loose mode). |
| Forgetting to bring link up after creating bridge or veth | Link stays in state `DOWN` and drops all incoming frames. | Always run `sudo ip link set dev <name> up`. |

## Performance, Security & Cost Implications

### Performance
- **Hardware Offloading**: Modern NICs support TCP Segmentation Offload (TSO), Generic Receive Offload (GRO), and Checksum Offload. Query and verify offload capabilities using `ethtool -k <interface>`.
- **Receive Side Scaling (RSS)**: Distributes network processing across multiple CPU cores by hashing packet 5-tuples onto distinct RX queues.

### Security
- **IP Forwarding Control**: By default, Linux disables packet forwarding between interfaces (`net.ipv4.ip_forward = 0`). Only enable forwarding on dedicated gateway or router/NAT nodes.
- **Strict Reverse Path Filtering**: Set `net.ipv4.conf.all.rp_filter = 1` to drop spoofed IP packets entering interfaces where the kernel would not route return traffic back through.

### Cost
- **Egress Routing Optimization**: In multi-cloud or hybrid environments, directing outbound traffic via internal DirectConnect / VPN gateways rather than public NAT gateways can reduce cloud data transfer egress fees significantly.

## Real-World Troubleshooting & Interview Q&A

### Q1: How do you verify which route and interface the Linux kernel will choose for a specific destination IP?
<details>
<summary>View Solution</summary>

Use `ip route get <destination_ip>`:
```bash
$ ip route get 1.1.1.1
1.1.1.1 via 192.168.1.1 dev enp3s0 src 192.168.1.50 uid 1000
    cache
```
The kernel executes the exact FIB lookup, displaying the selected egress interface (`dev enp3s0`), the next-hop gateway (`via 192.168.1.1`), and the source IP chosen for outbound packets (`src 192.168.1.50`).
</details>

### Q2: What causes "asymmetric routing" on a multi-homed server and why does it break TCP?
<details>
<summary>View Solution</summary>

**Asymmetric routing** occurs when an inbound packet enters via Interface A (e.g., secondary NIC `10.0.0.50`), but the response packet exits via Interface B (the primary default gateway `192.168.1.1`).

**Why it breaks**:
1. Stateful firewalls or NAT gateways along the path drop the packet because they see outbound replies without the corresponding initial `SYN`.
2. Linux kernel Reverse Path Filtering (`rp_filter = 1`) drops the incoming packet immediately if the return path does not route back out through the same interface.

**Solution**: Implement Policy-Based Routing (PBR) using `ip rule` and separate routing tables.
</details>

### Q3: How do you safely test a Netplan configuration on a remote server over SSH without risking being locked out?
<details>
<summary>View Solution</summary>

Use `sudo netplan try`:
```bash
sudo netplan try
```
`netplan try` applies the configuration temporarily and presents a prompt: `Configuration accepted? (Press ENTER within 120 seconds to confirm)`. If you lose SSH connectivity due to a misconfigured IP, subnet, or gateway, the timer expires and Netplan automatically restores the previous working configuration.
</details>

### Q4: What is the difference between `/etc/hosts` and the routing table?
<details>
<summary>View Solution</summary>

- `/etc/hosts` operates at the **Application Layer (Layer 7)** for Name Resolution (mapping hostname strings like `db.internal` to IP addresses like `10.0.0.5`).
- The **Routing Table** operates at the **Network Layer (Layer 3)** inside the kernel (determining which network interface and physical next-hop gateway to use to transmit packets destined for `10.0.0.5`).
</details>

### Q5: How do you check if IP forwarding is enabled, and how do you enable it permanently?
<details>
<summary>View Solution</summary>

```bash
# Check runtime status (0 = disabled, 1 = enabled)
sysctl net.ipv4.ip_forward

# Enable at runtime immediately:
sudo sysctl -w net.ipv4.ip_forward=1

# Persist permanently across reboots:
echo "net.ipv4.ip_forward = 1" | sudo tee /etc/sysctl.d/99-ipforward.conf
sudo sysctl --system
```
</details>

### Q6: What does the `metric` parameter in a routing table signify?
<details>
<summary>View Solution</summary>

The `metric` indicates the routing cost or priority of a route. If a system has multiple routes to the same destination network (e.g., two default gateways across Ethernet and Wi-Fi):
- The kernel selects the route with the **lowest metric number**.
- Example: A default route with `metric 100` is preferred over a default route with `metric 600`.
</details>

### Q7: How do you create a virtual ethernet pair (`veth`) and why are they used?
<details>
<summary>View Solution</summary>

A `veth` pair acts like a virtual bidirectional network cable: packets transmitted into one end emerge immediately at the other end. They are the backbone of container networking (Docker, Podman, Kubernetes).
```bash
# Create pair
sudo ip link add veth-host type veth peer name veth-guest

# Move one peer into a network namespace
sudo ip link set veth-guest netns container-ns
```
</details>

### Q8: What is the purpose of the `proto kernel` flag in `ip route` output?
<details>
<summary>View Solution</summary>

`proto kernel` indicates that the route was created automatically by the Linux kernel itself when an IP address was assigned to an active interface, representing the directly connected subnet. Routes installed by administrators show `proto static`, while routes installed by routing daemons show `proto zebra`, `proto bgp`, or `proto ospf`.
</details>
