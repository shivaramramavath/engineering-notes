# Error Handling Architecture and RFC 7807 in FastAPI

## 1. Conceptual Foundation & Mental Model

### The Chaos of Inconsistent Error Payloads
In unarchitected FastAPI services, error responses frequently fragment into multiple conflicting formats:
- FastAPI's default validation error: `{"detail": [{"loc": [...], "msg": "..."}]}`
- Ad-hoc developer exceptions: `{"error": "User not found"}` or `{"message": "Payment failed", "code": 400}`
- Uncaught 500 exceptions leaking internal Python stack traces, SQL syntax errors, and database connection strings to public clients.

This lack of standardization frustrates frontend and mobile developers, who must write complex defensive parsing logic for every endpoint.

### The RFC 7807 / RFC 9457 Standard: Problem Details for HTTP APIs
**RFC 7807** (and its modern successor **RFC 9457**) establishes a standardized machine-readable JSON structure for communicating errors from HTTP APIs:
- `type` (URI): A URI reference that identifies the specific problem type (e.g., `"https://api.example.com/errors/insufficient-funds"`).
- `title` (string): A short, human-readable summary of the problem type (e.g., `"Insufficient Funds"`).
- `status` (integer): The HTTP status code generated by the origin server for this occurrence of the problem.
- `detail` (string): A human-readable explanation specific to this occurrence of the problem.
- `instance` (URI): A URI reference that identifies the specific occurrence of the problem (e.g., request correlation ID or URL).

```json
{
  "type": "https://api.myplatform.com/errors/resource-not-found",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "Customer with ID 'cust_42' does not exist.",
  "instance": "/api/v1/customers/cust_42",
  "correlation_id": "req_88f9104c-3e1b-4029"
}
```

## 2. Architecture & Internal Mechanics

Understanding the pipeline through which exceptions bubble from the domain core up to FastAPI's centralized exception handling layer.

```
+-------------------------------------------------------------+
|                      DOMAIN / SERVICE LAYER                 |
|  Raises custom DomainError (e.g., InsufficientStockError)   |
|  (Contains ZERO HTTP concepts or status codes)              |
+-------------------------------------------------------------+
                              |
                              v (Bubbles up through Call Stack)
+-------------------------------------------------------------+
|                     PRESENTATION ROUTER                     |
|  Does NOT catch domain error; allows it to escape cleanly   |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                 CENTRAL EXCEPTION REGISTRY                  |
|  FastAPI @app.exception_handler(DomainError)                |
|  1. Intercepts specific DomainError subclass                |
|  2. Extracts Request Correlation ID from context            |
|  3. Logs structured error with stack trace (if 500)         |
|  4. Formats uniform RFC 7807 JSON Response                  |
+-------------------------------------------------------------+
                              |
                              v
                      [HTTP Client / UI]
```

### Decoupled Exception Taxonomy
Business exceptions are organized in an inheritance tree rooted at `DomainError`:
- `DomainError` (Base)
  - `EntityNotFoundError` $\longrightarrow$ Maps to `404 Not Found`
  - `ConflictError` $\longrightarrow$ Maps to `409 Conflict`
  - `BusinessRuleViolationError` $\longrightarrow$ Maps to `422 Unprocessable Entity`
  - `UnauthorizedError` $\longrightarrow$ Maps to `401 Unauthorized`
  - `ForbiddenError` $\longrightarrow$ Maps to `403 Forbidden`

## 4. Practical Implementation: 5 Verified Examples

### Example 1: Domain Exception Hierarchy
Pure Python exceptions representing domain failures without any HTTP transport dependencies.

```python
# app/core/exceptions.py
class DomainError(Exception):
    """Base exception for all domain logic failures."""
    def __init__(self, message: str, code: str = "DOMAIN_ERROR"):
        self.message = message
        self.code = code
        super().__init__(message)

class EntityNotFoundError(DomainError):
    def __init__(self, entity_name: str, entity_id: str):
        self.entity_name = entity_name
        self.entity_id = entity_id
        super().__init__(f"{entity_name} with ID '{entity_id}' not found", code="ENTITY_NOT_FOUND")

class BusinessRuleViolationError(DomainError):
    def __init__(self, message: str, rule_name: str):
        self.rule_name = rule_name
        super().__init__(message, code=f"RULE_VIOLATION_{rule_name.upper()}")

class DuplicateResourceError(DomainError):
    def __init__(self, resource: str, identifier: str):
        self.resource = resource
        self.identifier = identifier
        super().__init__(f"{resource} with identifier '{identifier}' already exists", code="DUPLICATE_RESOURCE")
```

### Example 2: RFC 7807 Centralized Exception Handlers
Mapping domain exceptions, validation errors, and uncaught 500 exceptions to uniform Problem Details responses.

```python
# app/core/error_handlers.py
import uuid
import logging
from fastapi import FastAPI, Request, status
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError
from starlette.exceptions import HTTPException as StarletteHTTPException
from app.core.exceptions import (
    DomainError,
    EntityNotFoundError,
    DuplicateResourceError,
    BusinessRuleViolationError,
)

logger = logging.getLogger(__name__)

def get_correlation_id(request: Request) -> str:
    """Retrieves correlation ID attached by middleware or generates a fallback."""
    return getattr(request.state, "correlation_id", str(uuid.uuid4()))

def register_exception_handlers(app: FastAPI) -> None:

    # 1. Handle Entity Not Found (404)
    @app.exception_handler(EntityNotFoundError)
    async def entity_not_found_handler(request: Request, exc: EntityNotFoundError):
        return JSONResponse(
            status_code=status.HTTP_404_NOT_FOUND,
            content={
                "type": "https://api.myplatform.com/errors/entity-not-found",
                "title": "Entity Not Found",
                "status": 404,
                "detail": exc.message,
                "instance": str(request.url.path),
                "code": exc.code,
                "correlation_id": get_correlation_id(request),
            },
        )

    # 2. Handle Duplicate / Conflict (409)
    @app.exception_handler(DuplicateResourceError)
    async def duplicate_resource_handler(request: Request, exc: DuplicateResourceError):
        return JSONResponse(
            status_code=status.HTTP_409_CONFLICT,
            content={
                "type": "https://api.myplatform.com/errors/duplicate-resource",
                "title": "Resource Conflict",
                "status": 409,
                "detail": exc.message,
                "instance": str(request.url.path),
                "code": exc.code,
                "correlation_id": get_correlation_id(request),
            },
        )

    # 3. Handle Business Invariant Violations (422)
    @app.exception_handler(BusinessRuleViolationError)
    async def business_rule_handler(request: Request, exc: BusinessRuleViolationError):
        return JSONResponse(
            status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
            content={
                "type": "https://api.myplatform.com/errors/business-rule-violation",
                "title": "Business Rule Violation",
                "status": 422,
                "detail": exc.message,
                "instance": str(request.url.path),
                "code": exc.code,
                "correlation_id": get_correlation_id(request),
            },
        )

    # 4. Standardize Pydantic Validation Errors (422)
    @app.exception_handler(RequestValidationError)
    async def validation_exception_handler(request: Request, exc: RequestValidationError):
        invalid_params = []
        for error in exc.errors():
            loc = " -> ".join(str(l) for l in error.get("loc", []))
            invalid_params.append({
                "field": loc,
                "message": error.get("msg", "Invalid value"),
                "type": error.get("type", "value_error"),
            })

        return JSONResponse(
            status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
            content={
                "type": "https://api.myplatform.com/errors/validation-error",
                "title": "Invalid Request Parameters",
                "status": 422,
                "detail": "The request payload failed schema validation rules.",
                "instance": str(request.url.path),
                "invalid_params": invalid_params,
                "correlation_id": get_correlation_id(request),
            },
        )

    # 5. Catch-All for Unhandled 500 Server Errors
    @app.exception_handler(Exception)
    async def unhandled_exception_handler(request: Request, exc: Exception):
        corr_id = get_correlation_id(request)
        # Log the full traceback internally for telemetry
        logger.critical("Unhandled server exception [%s]: %s", corr_id, exc, exc_info=True)

        # Return a safe, sanitized error message to the client
        return JSONResponse(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            content={
                "type": "https://api.myplatform.com/errors/internal-server-error",
                "title": "Internal Server Error",
                "status": 500,
                "detail": "An unexpected server error occurred. Please contact support with this correlation ID.",
                "instance": str(request.url.path),
                "correlation_id": corr_id,
            },
        )
```

### Example 3: Correlation ID Middleware
Ensuring every request carries a correlation ID accessible to error handlers and logging pipelines.

```python
# app/core/middleware.py
import uuid
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request

class CorrelationIdMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        # Read incoming X-Correlation-ID or generate new UUID
        correlation_id = request.headers.get("X-Correlation-ID") or f"req_{uuid.uuid4().hex[:12]}"
        request.state.correlation_id = correlation_id

        response = await call_next(request)
        response.headers["X-Correlation-ID"] = correlation_id
        return response
```

from pydantic import BaseModel, Field
from app.core.exceptions import EntityNotFoundError, BusinessRuleViolationError

router = APIRouter(prefix="/orders", tags=["Orders"])

class OrderRequest(BaseModel):
    product_sku: str = Field(min_length=3)
    quantity: int = Field(gt=0, le=100)

@router.get("/{order_id}")
async def get_order(order_id: str):
    # Simulated domain service call
    if order_id == "missing_123":
        raise EntityNotFoundError(entity_name="Order", entity_id=order_id)
    return {"order_id": order_id, "status": "CONFIRMED"}

@router.post("/")
async def create_order(payload: OrderRequest):
    if payload.product_sku == "OUT_OF_STOCK":
        raise BusinessRuleViolationError(
            message="Item is discontinued and cannot be purchased",
            rule_name="discontinued_inventory"
        )
    return {"status": "CREATED", "sku": payload.product_sku}

## 5. Edge Cases, Pitfalls & Failure Modes

1. **Leaking Stack Traces in 500 Responses**: Default Starlette exception handlers can output full Python tracebacks when `debug=True`. In production, `debug` must be `False`, and unhandled exception handlers must return sanitized messages to prevent database credentials from leaking.
2. **Double Exception Wrapping**: If an exception handler itself raises an unhandled exception, the ASGI server aborts abruptly, returning a raw, plain-text HTTP 500 without headers or correlation IDs. Always keep exception handlers simple and defensive.
3. **Pydantic Validation Error Shape Changes**: Pydantic v2 changed the internal structure of validation errors (e.g., `loc` tuple format). Hardcoding assumptions about error dictionary keys without safe `.get()` calls can trigger `KeyError` inside the exception handler.
4. **Header Stripping on Error Responses**: If an exception occurs inside a route handler before middleware finishes, default Starlette error responses may drop headers (like `X-Correlation-ID` or `Access-Control-Allow-Origin`). Ensure exception handlers explicitly read `request.state.correlation_id`.

## 6. Common Mistakes Table

| Mistake | Root Cause | Impact | Correct Approach |
| :--- | :--- | :--- | :--- |
| **Scattering `try/except HTTPException` in Routes** | Lack of centralized architecture | Massive boilerplate; inconsistent error schemas across endpoints. | Raise domain exceptions in services; handle them globally with `@app.exception_handler`. |
| **Returning Raw Python Exceptions to Clients** | Omitting catch-all 500 handler | Leaks internal database table names, SQL syntax, and file paths. | Catch `Exception` globally; log traceback privately and return generic RFC 7807 payload. |
| **Using Different Error JSON Keys per Route** | Ad-hoc error formatting | Frontend clients break; cannot build unified error toast/alert components. | Standardize strictly on RFC 7807 / RFC 9457 Problem Details schema. |
| **Omitting Correlation IDs in Error Bodies** | Failing to pass request context | Users report "it failed", but engineers cannot find corresponding server logs. | Attach `correlation_id` to both HTTP headers and JSON error bodies. |
| **Using HTTP Status Code 200 for Errors** | GraphQL habits in REST APIs | Breaks HTTP caching, reverse proxies, and automated retry policies. | Use semantically accurate HTTP status codes (400, 401, 403, 404, 409, 422, 500). |
| **Raising `HTTPException` Inside the Domain Core** | Importing FastAPI in business entities | Business logic cannot run in CLI tools, background workers, or Kafka consumers. | Raise pure Python `DomainError` subclasses in the core. |

## 7. Performance & Scalability Considerations

- **Exception Construction Overhead**: In Python, creating exceptions and capturing stack traces (`sys.exc_info()`) has a minor CPU cost (~5 microseconds). Avoid using exceptions for normal, predictable control flow (e.g., end-of-list iteration).
- **Log Buffering on Outages**: If a database outage causes 10,000 requests per second to throw 500 errors, synchronous file logging can saturate disk I/O. Use asynchronous non-blocking loggers (`structlog` or `loguru` with enqueue).
- **Free-Threading in Python 3.13t**: Error handler JSON serialization using Pydantic v2 and `orjson` scales across multi-threaded workers without GIL contention.

## 8. Security & OWASP Guardrails

- **OWASP A05 (Security Misconfiguration - Information Leakage)**: Never expose database error messages (e.g., `asyncpg.exceptions.UniqueViolationError: Key (email)=(admin@test.com) already exists`). Map them to sanitized messages: `"A resource with the specified identifier already exists."`
- **OWASP A09 (Security Logging and Monitoring Failures)**: Every error response must log the correlation ID, requesting user ID, IP address, and timestamp to enable audit trails during security incidents.

## 10. Real-World Case Study / Production Incident

A mobile banking application experienced an outage during high-volume Black Friday traffic. Users attempting to transfer funds received generic error popups.

**The Failure**:
1. When a user attempted a transfer exceeding their balance, the database threw a foreign key violation or lock timeout.
2. The route handler did not catch the error, allowing Starlette's raw handler to output an unformatted HTML error page with a full SQL query trace.
3. The mobile application's JSON parser crashed because it received HTML instead of JSON. The mobile app went into an infinite crash-and-restart loop for 12,000 customers.
4. Security researchers reported that the leaked SQL traces revealed the internal column names of the bank's core balance ledger.

**The Solution**:
The engineering team implemented the RFC 7807 error handling architecture:
- Registered a catch-all exception handler that guaranteed all responses were valid `application/problem+json`, completely preventing mobile app parser crashes.
- All internal database tracebacks were directed to an internal Sentry telemetry cluster, while users received clean, sanitized RFC 7807 responses containing a correlation ID for customer support.

## 11. Technical Interview Questions

<details>
<summary>1. What is RFC 7807 / RFC 9457, and why is it recommended for REST APIs?</summary>
RFC 7807 (and its updated revision RFC 9457) is an IETF specification defining "Problem Details for HTTP APIs". It standardizes the format of HTTP error responses into a consistent JSON object with fields like `type`, `title`, `status`, `detail`, and `instance`. Standardizing on this specification prevents endpoint error fragmentation, eliminates custom parsing logic in client applications, and enables automated error handling across frontend clients.
</details>

<details>
<summary>2. Why should the Service and Domain layers avoid raising `fastapi.HTTPException`?</summary>
Raising `HTTPException` couples the domain and business logic to the HTTP transport protocol. If the service is subsequently reused in a CLI tool, a background Celery worker, an event subscriber, or a gRPC service, raising an HTTP-specific exception makes no semantic sense. High-level services should raise pure domain exceptions, allowing presentation-layer exception handlers to map them to appropriate HTTP status codes.
</details>

<details>
<summary>3. What is the role of a Correlation ID in error handling architecture?</summary>
A Correlation ID (or Request ID) is a unique identifier assigned to an incoming HTTP request at the reverse proxy or API gateway. When an error occurs, the correlation ID is included in both the server logs and the client error response body. This allows engineers to instantly locate the exact server logs and stack trace corresponding to a user-reported error.
</details>

<details>
<summary>4. How does FastAPI's `@app.exception_handler()` mechanism work under the hood?</summary>
FastAPI registers exception handlers in Starlette's `ExceptionMiddleware`. When an unhandled exception bubbles out of a route handler, the middleware intercepts it and traverses its registered exception mapping using `isinstance()` checks. If a matching handler is found, it passes the `Request` and `Exception` instances to the handler, returning the resulting `Response`.
</details>

<details>
<summary>5. What is the difference between HTTP 400, HTTP 422, and HTTP 409 status codes?</summary>
- **HTTP 400 (Bad Request)**: Malformed syntax, invalid JSON formatting, or unparseable headers.
- **HTTP 422 (Unprocessable Entity)**: Well-formed syntax and valid JSON, but semantic validation failure (e.g., negative balance, missing required business fields, or Pydantic validation errors).
- **HTTP 409 (Conflict)**: The request conflicts with current server state (e.g., duplicate unique email registration or concurrent optimistic locking conflict).
</details>

<details>
<summary>6. How do you override FastAPI's default Pydantic validation error response?</summary>
By registering a custom exception handler for `fastapi.exceptions.RequestValidationError`:
```python
@app.exception_handler(RequestValidationError)
async def custom_validation_handler(request: Request, exc: RequestValidationError):
    # Format custom response
    return JSONResponse(status_code=422, content=...)
```
</details>

<details>
<summary>7. Why must `debug=False` always be configured in production FastAPI deployments?</summary>
When `debug=True`, Starlette catches unhandled exceptions and returns an interactive HTML error page displaying the entire Python traceback, local variable values, environment configurations, and source code snippets. This presents an extreme security risk (OWASP Information Disclosure).
</details>

<details>
<summary>8. How should an API differentiate between expected business errors and unexpected server crashes?</summary>
Expected business errors (e.g., insufficient stock, wrong password) are represented by explicit `DomainError` subclasses and return 4xx status codes with user-friendly explanations. Unexpected server crashes (database disconnects, unhandled `NullPointer`/`AttributeError`) are caught by the catch-all `Exception` handler, logged with full stack traces, and returned to clients as a sanitized 500 Internal Server Error with a correlation ID.
</details>

<summary>Exercise 3 (Medium): RFC 7807 Validation Error Formatter</summary>

**Task**: Write an exception handler for `RequestValidationError` that transforms Pydantic's error list into a flat list of `{"field": "...", "reason": "..."}` objects inside an RFC 7807 response.

**Solution**:
```python
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

@app.exception_handler(RequestValidationError)
async def rfc7807_validation_handler(request: Request, exc: RequestValidationError):
    errors = []
    for err in exc.errors():
        field_path = ".".join(str(loc) for loc in err["loc"] if loc != "body")
        errors.append({"field": field_path, "reason": err["msg"]})

    return JSONResponse(
        status_code=422,
        content={
            "type": "https://api.example.com/errors/validation-failed",
            "title": "Validation Failed",
            "status": 422,
            "detail": "One or more fields failed validation.",

        }
    )

logger = logging.getLogger("api.errors")

            "status": 500,
            "detail": "An internal error occurred. Please contact support with the trace identifier.",

            "trace_id": trace_id,
        }
    )
```
