# S3

S3 is object storage: you put bytes under a **key** in a **bucket**, and read them back by key. There are no real folders, no file locking and no in-place edits; an object is replaced whole. In a Node backend it holds uploads, generated reports, static assets and the inputs/outputs of pipelines, and it's often the thing that *triggers* other work ([event-driven Lambda](../03-lambda/03-event-driven-lambda.md)).

Prerequisites: [SDK v3 and credentials](../01-setup/01-sdk-v3-and-credentials.md) (clients, regions) and a bucket in the same region as your client.

```bash
npm install @aws-sdk/client-s3 @aws-sdk/s3-request-presigner @aws-sdk/lib-storage @aws-sdk/s3-presigned-post
```

---

## The mental model

- **Bucket**: a globally unique name, lives in one region.
- **Key**: any UTF-8 string, e.g. `uploads/42/avatar.png`. The `/` is just a character. The console shows "folders" by grouping on a *prefix*.
- **Object**: bytes + metadata (`ContentType`, `ContentLength`, `ETag`, custom metadata). Max single object is 5 TiB.
- **Consistency**: reads after writes are strongly consistent. Put an object, read it immediately, you get the new version.
- **Defaults on new buckets**: Block Public Access is on and objects are encrypted at rest (SSE-S3). Keep it that way; share data with presigned URLs or CloudFront, not public buckets.

## Basic operations

```ts
import {
  S3Client, PutObjectCommand, GetObjectCommand, HeadObjectCommand,
  DeleteObjectCommand, CopyObjectCommand,
} from "@aws-sdk/client-s3";

const s3 = new S3Client({ region: process.env.AWS_REGION });
const Bucket = process.env.UPLOADS_BUCKET!;

// write
await s3.send(new PutObjectCommand({
  Bucket,
  Key: "reports/2026-10.json",
  Body: JSON.stringify({ total: 42 }),
  ContentType: "application/json",
}));

// read
const res = await s3.send(new GetObjectCommand({ Bucket, Key: "reports/2026-10.json" }));
const text = await res.Body!.transformToString();

// metadata only (no body): does it exist, how big?
const head = await s3.send(new HeadObjectCommand({ Bucket, Key: "reports/2026-10.json" }));
console.log(head.ContentLength, head.ContentType, head.ETag);

// delete (succeeds even if the key doesn't exist)
await s3.send(new DeleteObjectCommand({ Bucket, Key: "reports/2026-10.json" }));
```

Things that surprise people:

- **Always set `ContentType`** on upload. Otherwise S3 stores `binary/octet-stream` and browsers will download instead of display.
- **`Body` on read is a stream**, not a string. `transformToString()`, `transformToByteArray()` and `transformToWebStream()` are helpers on it. Use them for small objects only; they buffer everything.
- **"Does it exist?"** is `HeadObjectCommand`. A missing key throws an error named `NotFound` (HEAD responses have no body, so no `NoSuchKey`). `GetObject` throws `NoSuchKey`.
- **Copy** uses `CopySource: "bucket/key"` and the key part must be URL-encoded.
- There's no rename or move: copy, then delete.

## Streams: big files without buffering

Downloading to disk, or proxying to an HTTP response, should stream so memory stays flat.

```ts
import { pipeline } from "node:stream/promises";
import { createWriteStream } from "node:fs";
import type { Readable } from "node:stream";

const res = await s3.send(new GetObjectCommand({ Bucket, Key }));
await pipeline(res.Body as Readable, createWriteStream("/tmp/out.bin"));
```

In Express, stream through to the client:

```ts
app.get("/files/:key", async (req, rep) => {
  const res = await s3.send(new GetObjectCommand({ Bucket, Key: req.params.key }));
  rep.setHeader("Content-Type", res.ContentType ?? "application/octet-stream");
  if (res.ContentLength) rep.setHeader("Content-Length", String(res.ContentLength));
  await pipeline(res.Body as Readable, rep);
});
```

(Don't let a client pick arbitrary keys in real code; map an ID to a key you control. For large downloads, a presigned URL below avoids proxying through your server at all.)

In Node, `res.Body` is a `Readable`, so the cast is safe. In browsers or edge runtimes it's a web `ReadableStream`, which is why the SDK types it as a union.

Uploading from a stream of unknown length is where plain `PutObject` fails; use `Upload` from `lib-storage`, next.

## Multipart uploads with `Upload`

A single `PutObject` handles up to 5 GB, but anything large or streamed should use multipart: the file is split into parts uploaded in parallel and assembled by S3. You rarely drive the raw multipart API; `@aws-sdk/lib-storage` does it.

```ts
import { Upload } from "@aws-sdk/lib-storage";
import { createReadStream } from "node:fs";

const upload = new Upload({
  client: s3,
  params: { Bucket, Key: "backups/db.dump", Body: createReadStream("/data/db.dump"), ContentType: "application/octet-stream" },
  partSize: 8 * 1024 * 1024, // min 5 MiB (except the last part)
  queueSize: 4,              // parts uploaded concurrently
  leavePartsOnError: false,  // abort and clean up if it fails
});

upload.on("httpUploadProgress", (p) => console.log(p.loaded, p.total));
await upload.done();
```

Rules: parts are 5 MiB to 5 GiB, at most 10,000 parts, so `partSize` has to be big enough that `fileSize / partSize <= 10000`. Bodies smaller than one part go as a normal single request automatically.

**Incomplete multipart uploads cost money and are invisible in normal listings.** Add a lifecycle rule on the bucket to abort incomplete uploads after a few days.

## Presigned URLs: let clients talk to S3 directly

The usual upload/download design: your API authorizes the user, then hands back a short-lived URL signed with *your* credentials. The browser transfers bytes straight to/from S3, so your server never proxies the file.

```text
Browser            Your API                 S3
   │  1. "I want to upload"  │               │
   ├────────────────────────▶│  2. sign URL  │
   │◀────────────────────────┤  (no S3 call) │
   │  3. PUT bytes to the URL                │
   ├────────────────────────────────────────▶│
   │  4. 200 OK                              │
   │◀────────────────────────────────────────┤
```

```ts
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";
import { randomUUID } from "node:crypto";

// upload
export async function createUploadUrl(userId: string, contentType: string) {
  const Key = `uploads/${userId}/${randomUUID()}`;           // key chosen by the server
  const url = await getSignedUrl(
    s3,
    new PutObjectCommand({ Bucket, Key, ContentType: contentType }),
    { expiresIn: 300 }
  );
  return { url, Key };
}

// download
const downloadUrl = await getSignedUrl(
  s3,
  new GetObjectCommand({ Bucket, Key, ResponseContentDisposition: 'attachment; filename="report.pdf"' }),
  { expiresIn: 300 }
);
```

Client side:

```ts
await fetch(url, { method: "PUT", headers: { "Content-Type": file.type }, body: file });
```

Rules and gotchas:

- Signing is **local**: no network call, and it doesn't check that the key exists or that you have permission. A bad URL fails when *used*, with `AccessDenied`.
- **A headers you sign must be sent.** If you signed `ContentType`, the client must send exactly that `Content-Type`, or S3 returns `SignatureDoesNotMatch`.
- **Expiry is capped by your credentials.** With temporary credentials (Lambda role, SSO) the URL stops working when the session credentials expire, even if `expiresIn` is longer.
- The URL is a bearer token: anyone holding it can use it until expiry. Keep expiries short, never log full URLs.
- **Browser uploads need CORS** on the bucket, or the preflight fails:

```json
[{
  "AllowedOrigins": ["https://app.example.com"],
  "AllowedMethods": ["PUT", "GET"],
  "AllowedHeaders": ["*"],
  "ExposeHeaders": ["ETag"],
  "MaxAgeSeconds": 3000
}]
```

### Enforcing size and type: presigned POST

A presigned PUT can't limit the upload size. `createPresignedPost` can, using policy conditions:

```ts
import { createPresignedPost } from "@aws-sdk/s3-presigned-post";

const { url, fields } = await createPresignedPost(s3, {
  Bucket,
  Key: `uploads/${userId}/${randomUUID()}`,
  Conditions: [
    ["content-length-range", 1, 10 * 1024 * 1024], // 1 byte to 10 MiB
    ["eq", "$Content-Type", "image/png"],
  ],
  Fields: { "Content-Type": "image/png" },
  Expires: 300,
});
// client: multipart/form-data POST to `url` with every field in `fields`, then the `file` field LAST
```

Presigned URL safety checklist: server-generated keys, per-user prefixes, short expiry, size/type limits where it matters, and validate the object after upload (the `ContentType` header is client-claimed, not proof of content).

## Listing and pagination

`ListObjectsV2` returns at most 1000 keys per call. Use the paginator rather than hand-rolling `ContinuationToken`.

```ts
import { paginateListObjectsV2 } from "@aws-sdk/client-s3";

const keys: string[] = [];
for await (const page of paginateListObjectsV2({ client: s3 }, { Bucket, Prefix: "uploads/42/" })) {
  keys.push(...(page.Contents ?? []).map((o) => o.Key!));
}
```

- Listing is by **prefix** and returns keys in lexicographic order. Add `Delimiter: "/"` to get `CommonPrefixes` (folder-like grouping).
- Listing is a billed, relatively slow call. Don't use it as a database; store keys in [DynamoDB](./02-dynamodb.md) if you need to query them.
- Delete in bulk with `DeleteObjectsCommand` (up to 1000 keys per call), and check the `Errors` array in the response, because the call can partly fail without throwing.

## Events: reacting to uploads

S3 can notify Lambda, SQS, SNS or EventBridge when an object is created. Two things bite people:

- **Object keys in events are URL-encoded** (spaces become `+`). Decode: `decodeURIComponent(key.replace(/\+/g, " "))`.
- Delivery is at-least-once, so handlers must be idempotent. Details in [event-driven Lambda](../03-lambda/03-event-driven-lambda.md).

Never write results back to the *same prefix* that triggers the event, or you'll create an infinite loop.

## Permissions

Bucket-level and object-level actions use different ARNs:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::my-app-uploads" },
    { "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::my-app-uploads/*" }
  ]
}
```

Without `s3:ListBucket`, asking for a missing key returns **403 `AccessDenied` instead of 404**. If you see `AccessDenied` on an object you expected to exist, this may be why. Presigned URLs carry the signer's permissions, so the signing role needs `GetObject`/`PutObject` too.

## Common mistakes

| Mistake | Fix |
|---|---|
| Reading `Body` as a string | It's a stream; use `transformToString()` or pipe it |
| No `ContentType` on upload | Always set it |
| Buffering a multi-GB file with `PutObject` | `Upload` from `lib-storage` or a presigned URL |
| `SignatureDoesNotMatch` on a presigned PUT | Client must send the exact signed headers (`Content-Type`) |
| Browser upload fails with a CORS error | Add a bucket CORS rule for the origin and method |
| Presigned URL dies early | Credentials expired before `expiresIn` |
| Client chooses the S3 key | Generate keys on the server |
| `NoSuchBucket` with a correct name | Client region differs from the bucket's region |
| Treating `Delete` as proof the object existed | It succeeds on missing keys; use `HeadObject` first if it matters |
| Handler triggers itself via S3 events | Separate input and output prefixes or buckets |
| Leaving multipart uploads incomplete | Lifecycle rule to abort them |

---

## Quick summary

- Bucket + key + bytes; "folders" are prefixes; reads after writes are consistent.
- Set `ContentType`; treat `Body` as a stream.
- Big or streamed uploads: `Upload` (multipart). Big downloads/uploads from browsers: presigned URLs.
- Presigned URLs sign locally, expire with the credentials, and must be used with the signed headers; use presigned POST for size limits; configure CORS.
- Paginate listings; S3 isn't a query engine.
- Event keys are URL-encoded; delivery is at-least-once.
- Object actions need `bucket/*`; add `s3:ListBucket` for sane 404s.
