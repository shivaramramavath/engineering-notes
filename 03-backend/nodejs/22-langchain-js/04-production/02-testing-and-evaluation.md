# Testing and Evaluation

LLM output is non-deterministic and "correct" is often fuzzy, so `expect(output).toBe("...")` doesn't work for most of the app. The practical approach is layers: ordinary tests for the deterministic parts, and **evaluations** (scored runs over a dataset) for the model-dependent parts.

> The evaluation example follows the LangSmith evaluation quickstart for JS/TS. Package names and signatures in the eval ecosystem move quickly, so verify against the current docs before copying.

**Prerequisites:** [Tracing and Debugging](./01-tracing-and-debugging.md)

---

## Test pyramid for LLM apps

```text
        ▲  Evaluations on real-ish data      (slow, costs money, statistical)
       ───  Integration tests with a real model (a few, property-based)
     ─────  Unit tests, no model calls        (fast, exact, run on every commit)
```

### 1. Unit tests (no model)

Test everything that is plain code, with your normal test runner (Vitest, Jest):

- Prompt rendering: `await prompt.invoke(vars)` gives the messages you expect, with no unescaped-brace bugs.
- Tool functions: call them directly with sample arguments; check outputs and error cases.
- Parsers, formatters, chunking logic, access-control filters.
- Message-trimming logic keeps tool-call and tool-result pairs together.

```ts
import { test, expect } from "vitest";

test("prompt includes context and question", async () => {
  const value = await prompt.invoke({ context: "C", question: "Q" });
  const text = JSON.stringify(value.toChatMessages());
  expect(text).toContain("C");
  expect(text).toContain("Q");
});
```

To test chains and agents without network calls, swap the model for a stub that returns scripted responses. Check `@langchain/core` for its testing utilities before rolling your own.

### 2. Integration tests (real model, few, tolerant)

A small set of tests that call the real model to verify wiring: keys work, tool calling works, structured output parses. Assert **properties**, not exact text:

- The response is non-empty.
- Structured output matches the schema (the schema parse already asserts this).
- The expected tool was called with arguments in the right shape.
- Required facts appear (`toContain("Paris")`).

Use `temperature: 0` to reduce noise. Don't run these on every keystroke; run them in CI on a schedule or before release. Expect occasional flakiness and design assertions so that it is rare.

### 3. Evaluations (dataset plus scoring)

For answer quality, run your app over a **dataset** of inputs and score the outputs. This is how you compare prompt versions, models and retrieval settings objectively.

---

## Building a dataset

A good dataset beats a clever evaluator. Sources, in order of value:

1. **Real failures** from traces and user reports. Each bug becomes a permanent test case.
2. **Real questions** (sampled, with sensitive data removed).
3. **Hand-written edge cases:** out-of-scope questions, ambiguous questions, prompt-injection attempts, empty input, very long input.
4. **Synthetic examples** generated by a model, reviewed by a human.

Include a reference answer where there is one. Start with 20 to 50 good examples; grow it over time.

## Running an evaluation in LangSmith

```ts
import { Client } from "langsmith";
import { evaluate } from "langsmith/evaluation";

// 1. Dataset
const client = new Client();
const dataset = await client.createDataset("support-qa", { description: "Support questions" });
await client.createExamples({
  datasetId: dataset.id,
  inputs: [{ question: "How do I reset my password?" }],
  outputs: [{ answer: "Use the 'Forgot password' link on the sign-in page." }],
});

// 2. Target: the thing under test. Call your real chain or agent.
async function target(inputs: { question: string }) {
  const answer = await ragChain.invoke({ question: inputs.question });
  return { answer };
}

// 3. Evaluators: functions that score a run
function nonEmpty({ outputs }: { outputs: { answer: string } }) {
  return { key: "non_empty", score: outputs.answer.trim().length > 0 ? 1 : 0 };
}

// 4. Run
await evaluate(target, {
  data: "support-qa",
  evaluators: [nonEmpty],
  experimentPrefix: "rag-baseline",
  maxConcurrency: 2,
});
```

Each run is an **experiment** you can open in the UI and compare against others side by side. The `target` is just your app's entry point, so the evaluation exercises the same code that serves users.

### Evaluator types

| Type | Example | Notes |
|---|---|---|
| **Code** (deterministic) | Valid JSON, contains citation, under length limit, correct tool called | Cheapest and most reliable. Use whenever possible |
| **Reference-based** | Exact or fuzzy match against the expected answer | Good for extraction and classification |
| **LLM-as-judge** | A model scores correctness or helpfulness against criteria | Handles fuzzy quality, but needs care |

The docs' quickstart builds an LLM judge with the `openevals` package (`createLLMAsJudge` with a correctness prompt) and wraps it as an evaluator. Treat that as the starting point for judge-style scoring.

### Using LLM judges well

- Judges are models: they have biases (prefer longer answers, prefer their own style) and make mistakes.
- Give the judge **specific criteria**, not "is this good?".
- **Calibrate**: hand-label a sample, check that the judge agrees with you, and revisit when you change judge model or prompt.
- Keep judge and system models separate where you can, and keep the judge's temperature low.
- Prefer several narrow evaluators (faithfulness, relevance, format) over one vague score.

## Evaluating RAG: separate the two halves

A wrong answer can mean retrieval failed or generation failed. Measure both:

| Question | Check |
|---|---|
| Did we retrieve the right chunk? | Hit rate: is the known-relevant source in the top-k? (Code evaluator over `retriever.invoke`) |
| Is the answer grounded in the retrieved text? | Faithfulness judge: every claim supported by the context |
| Does it answer the question? | Relevance judge or reference comparison |
| Does it refuse out-of-scope questions? | Dataset of unanswerable questions; check for "I don't know" |

Fix retrieval first. A great prompt can't rescue missing context. See [Retrieval and RAG](../02-rag/03-retrieval-and-rag.md).

## Evaluating agents

- **Final outcome:** did the task get done correctly?
- **Trajectory:** did it use sensible tools in a sensible order, without loops or unneeded calls?
- **Cost and latency:** number of model calls, tokens, wall-clock time.
- **Safety:** did it refuse or escalate when it should? Test with injection attempts and requests that need approval.

Assert on the tool calls in `result.messages` in addition to the final answer.

---

## Making it routine

- Run the dataset on every change to prompts, model, retrieval settings, or tools.
- Compare against the previous experiment; **look at individual regressions**, not just the average.
- Gate releases on a threshold for key metrics, but keep a human review for judge-scored ones.
- Add every production bug to the dataset.
- Track cost and latency alongside quality; a better answer that costs ten times more may not be a win.

## Common mistakes

| Mistake | Fix |
|---|---|
| Exact-string asserts on model output | Assert properties, or use evaluators |
| Testing only the happy path | Add out-of-scope, adversarial and empty-input cases |
| One tiny, hand-picked dataset that never changes | Grow it from real failures |
| Trusting an LLM judge blindly | Calibrate against human labels |
| Looking only at the average score | Inspect individual regressions |
| Evaluating RAG only end-to-end | Measure retrieval and generation separately |
| Running live-model tests on every commit | Keep unit tests model-free; run model tests on a schedule or at release |
| Ignoring cost and latency in comparisons | Record them per experiment |
| Changing several things at once | Change one variable per experiment |

---

## Quick Summary

- Layer it: model-free unit tests, a few tolerant integration tests, and dataset-based evaluations.
- A dataset built from real failures is the most valuable asset.
- Evaluators can be code, reference-based or LLM judges; prefer code where it fits and calibrate judges.
- Evaluate RAG retrieval and generation separately; evaluate agents on outcome, trajectory and cost.
- Re-run evaluations on every change and compare experiments.
