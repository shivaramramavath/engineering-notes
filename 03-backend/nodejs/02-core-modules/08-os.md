# `os` — Operating System Information

Node's built-in module for getting information about the machine the process is running on — CPU, memory, network interfaces, and platform details. Used far less often than `fs`/`http`, but comes up for diagnostics, logging, and scaling decisions.

```js
import os from "node:os";
```

## Basic system info

```js
os.platform(); // "linux", "darwin", "win32"
os.arch(); // "x64", "arm64"
os.type(); // "Linux", "Darwin", "Windows_NT"
os.release(); // kernel/OS release version
os.hostname(); // the machine's hostname
os.uptime(); // seconds since the OS booted (not the Node process — see process.uptime())
```

```js
console.log(`Running on ${os.type()} ${os.release()} (${os.arch()})`);
```

---

## CPU information

```js
os.cpus();
```

```js
[
  {
    model: "Intel(R) Core(TM) i7-9750H CPU @ 2.60GHz",
    speed: 2600,
    times: { user: 123456, nice: 0, sys: 12345, idle: 987654, irq: 0 },
  },
  // one entry per logical core
];
```

```js
os.cpus().length; // number of logical CPU cores available
```

### Why this matters: deciding how many processes to run

```js
import os from "node:os";
import cluster from "node:cluster";

const numCPUs = os.cpus().length;

if (cluster.isPrimary) {
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }
}
```

Node itself is single-threaded for JavaScript execution — `os.cpus().length` is exactly how tools like `cluster` (`10-cluster-worker-threads.md`) and process managers like PM2 (`deployment/pm2.md`) decide how many worker processes to spin up to actually use every core on the machine.

## Memory information

```js
os.totalmem(); // total system RAM, in bytes
os.freemem(); // currently free RAM, in bytes
```

```js
const usedPercent = (1 - os.freemem() / os.totalmem()) * 100;
console.log(`Memory usage: ${usedPercent.toFixed(1)}%`);
```

Note the distinction from `process.memoryUsage()` (`07-process.md`) — that reports memory used by **this Node process specifically**; `os.totalmem()`/`freemem()` report the **whole machine's** memory, across every process running on it.

---

## Network interfaces

```js
os.networkInterfaces();
```

```js
{
  eth0: [
    { address: "192.168.1.42", family: "IPv4", internal: false, ... },
    { address: "fe80::...", family: "IPv6", internal: false, ... },
  ],
  lo: [
    { address: "127.0.0.1", family: "IPv4", internal: true, ... },
  ],
}
```

Occasionally useful for finding the machine's actual LAN IP (e.g. to log what address a dev server is reachable at), rather than just `localhost`.

## Temp directory and path conventions

```js
os.tmpdir(); // "/tmp" on Linux/macOS, "C:\Users\...\Temp" on Windows
os.homedir(); // the current user's home directory
os.EOL; // "\n" on POSIX, "\r\n" on Windows — the OS's line-ending convention
```

```js
import path from "node:path";
import os from "node:os";

const tempFile = path.join(os.tmpdir(), "upload-cache.tmp");
```

Using `os.tmpdir()` rather than hardcoding `/tmp` is what keeps this kind of code portable across operating systems — same reasoning as using `path.join()` instead of manual string concatenation (`02-path.md`).

## Load average (Unix only)

```js
os.loadavg(); // [1min, 5min, 15min] average system load
```

```
[0.52, 0.61, 0.58]
```

Returns `[0, 0, 0]` on Windows, which doesn't have an equivalent concept — this is a Unix-specific metric representing how many processes were, on average, waiting for CPU time over each window.

---

## Where this actually gets used

In practice, `os` shows up in a fairly narrow set of situations:

- **Scaling decisions** — `os.cpus().length` to decide worker/process counts (`cluster`, PM2, worker pools)
- **Health checks / diagnostics endpoints** — reporting memory/CPU info as part of an app's `/health` or `/status` route
- **Cross-platform file paths** — `os.tmpdir()`/`os.homedir()` instead of hardcoded, OS-specific paths
- **Logging context** — including hostname/platform in structured logs (ties into `logging/pino.md`) to identify which machine/instance produced a given log line in a multi-instance deployment

You'll reach for this module far less often than `fs`, `path`, or `http`, but it's the right tool whenever you need actual facts about the underlying machine rather than about your application's own state (which is what `process`, `07-process.md`, is for).

## Quick summary

- `os` reports facts about the **machine**; `process` reports facts about **this specific Node process** running on it — don't confuse `os.totalmem()`/`freemem()` with `process.memoryUsage()`
- `os.cpus().length` is the standard way to determine how many worker processes to spawn for full CPU utilization
- `os.tmpdir()`/`homedir()` give portable, cross-platform paths instead of hardcoding OS-specific locations
- `os.loadavg()` is Unix-only and returns zeros on Windows
