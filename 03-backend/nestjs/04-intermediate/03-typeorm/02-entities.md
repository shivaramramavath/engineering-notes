# Entities

An entity is a class that maps to a database table. Decorators describe the table, columns, indexes, and constraints; TypeORM maps rows to instances of the class. This note covers defining entities well, including the column-type gotchas that bite in production.

Prerequisites: [Setup](./01-setup.md), [DTO vs entity](../../03-core-concepts/02-validation-and-serialization/01-dto.md).

## A first entity

```ts
// users/user.entity.ts
import {
  Column, CreateDateColumn, DeleteDateColumn, Entity, Index,
  PrimaryGeneratedColumn, UpdateDateColumn,
} from 'typeorm';

export enum Role { User = 'user', Admin = 'admin' }

@Entity('users')                                       // explicit table name
export class User {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Index({ unique: true })
  @Column({ length: 255 })
  email: string;

  @Column({ select: false })                           // not loaded by default queries
  passwordHash: string;

  @Column({ type: 'enum', enum: Role, default: Role.User })
  role: Role;

  @Column({ default: true })
  active: boolean;

  @CreateDateColumn()
  createdAt: Date;

  @UpdateDateColumn()
  updatedAt: Date;

  @DeleteDateColumn()                                  // enables soft delete
  deletedAt?: Date;
}
```

Notes:

- With `strictPropertyInitialization`, properties need `!` or you relax the setting. The Nest scaffold disables it.
- Name tables explicitly (`@Entity('users')`). Defaults depend on the naming strategy, and some natural class names (`User`, `Order`) are reserved words in some databases. TypeORM quotes identifiers, but explicit names avoid surprises.
- Column names default to the **property name** (`createdAt`), which in PostgreSQL means a quoted camelCase column that's awkward in raw SQL. Many teams use a snake_case naming strategy (a community package or your own `NamingStrategyInterface`) or set `name` per column: `@Column({ name: 'created_at' })`. Decide once, early, because changing it later is a migration.

## Primary keys

| Decorator | Result |
|-----------|--------|
| `@PrimaryGeneratedColumn()` | Auto-increment integer |
| `@PrimaryGeneratedColumn('uuid')` | UUID generated by the DB (PostgreSQL) or by TypeORM, depending on the driver |
| `@PrimaryColumn()` | You supply the value (natural keys, externally generated IDs) |
| `@PrimaryColumn()` on several properties | Composite key |

UUIDs avoid enumeration and are safe to generate in distributed systems; auto-increment integers are smaller and index-friendlier. Pick per project, not per table, for consistency.

## Columns and types

```ts
@Column()                                    // type inferred from the TS type (string → varchar, number → integer, ...)
@Column({ type: 'varchar', length: 100 })
@Column({ type: 'text', nullable: true })
@Column({ type: 'int', default: 0 })
@Column({ type: 'decimal', precision: 10, scale: 2 })
@Column({ type: 'jsonb', default: {} })      // PostgreSQL JSON
@Column({ type: 'timestamptz' })
@Column('simple-array')                      // stored as comma-separated text (limited)
```

Common options: `nullable`, `default`, `unique`, `length`, `select`, `name`, `transformer`, `comment`.

**Important: type inference is limited and column types are database-specific.** `jsonb`, `timestamptz`, `uuid`, and `enum` behavior differ across PostgreSQL, MySQL, and SQLite. If you target one database, use its precise types; if you need portability, test on each.

### Gotchas worth memorizing

- **`decimal`/`numeric` and `bigint` come back as strings** from the PostgreSQL driver (to avoid precision loss), even if the property is typed `number`. Use a transformer, or handle money as integer minor units (cents) or a decimal library:

```ts
const decimalTransformer = {
  to: (v?: number) => v,
  from: (v?: string | null) => (v == null ? v : parseFloat(v)),
};

@Column({ type: 'decimal', precision: 10, scale: 2, transformer: decimalTransformer })
price: number;
```

Floating-point conversion is fine for display, not for money arithmetic. Prefer integer cents or a decimal library for real financial calculations.

- **Nullable columns need `nullable: true` and an honest TS type** (`string | null`). Otherwise TypeScript says it's always there while the database says otherwise. Also note TypeORM infers `Object` for union types like `string | null`, so specify `type` explicitly on nullable union columns: `@Column({ type: 'varchar', nullable: true })`.
- **Enums:** `type: 'enum'` creates a database enum on PostgreSQL/MySQL, and changing the enum later requires a migration. Some teams prefer a `varchar` plus a `CHECK` constraint, or a lookup table, for easier evolution.
- **Dates:** prefer `timestamptz` on PostgreSQL to avoid timezone ambiguity, and keep application dates in UTC.

## Special columns

| Decorator | Behavior |
|-----------|----------|
| `@CreateDateColumn()` | Set automatically on insert |
| `@UpdateDateColumn()` | Updated automatically on `save`/`update` through the ORM |
| `@DeleteDateColumn()` | Set by `softDelete()`/`softRemove()`; queries exclude soft-deleted rows by default |
| `@VersionColumn()` | Integer incremented on each `save` (see [optimistic locking](./07-transactions.md)) |

Soft delete in practice:

```ts
await users.softDelete(id);                       // sets deletedAt
await users.find();                               // excludes soft-deleted
await users.find({ withDeleted: true });          // includes them
await users.restore(id);                          // clears deletedAt
```

Unique constraints interact badly with soft delete: a soft-deleted row still occupies its unique value, so the same email can't be re-registered. Use a partial unique index (`WHERE deleted_at IS NULL`, PostgreSQL) via a migration if you need that. See [soft delete](../../08-architecture-and-patterns/04-real-world-patterns/02-soft-delete.md).

## Indexes and constraints

```ts
@Entity('orders')
@Index(['userId', 'status'])                 // composite index (order matters)
@Index(['reference'], { unique: true })
export class Order {
  @Column() userId: string;
  @Column() status: string;
  @Column() reference: string;
}
```

Index design and `EXPLAIN` are covered in [indexing and query basics](../02-database-foundations/06-indexing-and-query-basics.md). Remember to index **foreign key columns**; PostgreSQL doesn't do it automatically.

## Hiding sensitive columns

`select: false` keeps a column out of normal `find`/QueryBuilder results:

```ts
@Column({ select: false }) passwordHash: string;
```

To load it deliberately (for login):

```ts
const user = await users.findOne({ where: { email }, select: { id: true, email: true, passwordHash: true } });
// or QueryBuilder: .addSelect('u.passwordHash')
```

This reduces accidental exposure but isn't a substitute for response DTOs or [serialization](../../03-core-concepts/02-validation-and-serialization/07-serialization.md): `save()` results and other code paths can still carry the value.

## Embedded entities

Group related columns without a separate table:

```ts
export class Address {
  @Column() street: string;
  @Column() city: string;
}

@Entity()
export class Company {
  @Column(() => Address)
  address: Address;      // columns: addressStreet, addressCity (prefix from the property name)
}
```

## Listeners and hooks

```ts
@Entity()
export class User {
  @BeforeInsert()
  @BeforeUpdate()
  normalizeEmail() {
    this.email = this.email.toLowerCase();
  }
}
```

Hooks (`@BeforeInsert`, `@AfterLoad`, ...) run only for operations on **entity instances** such as `save()`/`remove()`. They do **not** run for `update()`, `delete()`, `insert()`, or QueryBuilder queries. Don't rely on hooks for invariants; put critical logic in services, or enforce it with database constraints. Hashing passwords in a hook is common but fragile for that reason; hashing in the service is more explicit.

## Active Record vs Data Mapper

TypeORM supports both:

```ts
// Active Record: the entity has save/find methods
export class User extends BaseEntity {}
await User.findOneBy({ id });

// Data Mapper (recommended in Nest): entities are plain classes, repositories do the work
await this.users.findOneBy({ id });
```

Data Mapper fits Nest's DI and testing (inject/mock repositories). Active Record's static methods are harder to mock and need the global connection.

## Entities are not DTOs

Don't accept entities as request bodies or return them directly:

- **Mass assignment:** a client can set `role` or `id` if the entity is the input type.
- **Leaking columns:** relations and internal fields appear in responses.

Use [DTOs](../../03-core-concepts/02-validation-and-serialization/01-dto.md) at the boundary and map. Class-transformer decorators work on entity instances because they're real classes ([serialization](../../03-core-concepts/02-validation-and-serialization/07-serialization.md)).

## Common mistakes

- **Relying on type inference for nullable or union types**, ending up with the wrong column type.
- **Treating `decimal`/`bigint` as numbers**; they arrive as strings.
- **Using `synchronize` to evolve the schema** instead of migrations.
- **Expecting hooks to run on `update()`/QueryBuilder.**
- **Soft delete + unique columns** without a partial unique index.
- **Using entities as DTOs.**
- **CamelCase columns in PostgreSQL** you later must always quote in raw SQL.
- **Using `simple-array`/`simple-json` for data you'll query or filter on.**
- **No indexes on foreign keys and common filter columns.**
- **Putting business logic in entity methods that depend on injected services** (entities aren't managed by Nest DI).

## Debugging

- `EntityMetadataNotFoundError: No metadata for "User"`: the entity isn't registered ([setup](./01-setup.md)).
- Column type mismatches after a change: generate a migration and **read it** ([migrations](./06-migrations.md)).
- Numbers failing `===` comparisons or arithmetic going wrong: you're probably holding strings from `decimal`/`bigint`.
- `passwordHash` undefined after `find`: it's `select: false`; select it explicitly where needed.
- `Data type "Object" in "User.x" is not supported`: a union/nullable property needs an explicit `type`.

## Quick Summary

- `@Entity('table')` + `@Column`/`@PrimaryGeneratedColumn` define the mapping; name tables and columns deliberately.
- Column types are database-specific; set them explicitly, especially for nullable/union types, JSON, enums, and dates.
- `decimal`/`bigint` return strings: use transformers or integer minor units.
- Use `@CreateDateColumn`, `@UpdateDateColumn`, `@DeleteDateColumn`, `@VersionColumn`; mind soft delete vs unique constraints.
- Hooks run only on entity-instance operations; don't rely on them for invariants.
- Use Data Mapper (repositories), and keep entities separate from DTOs.
