# Schema

`schema.prisma` is the single source of truth for your data model: tables, columns, constraints, indexes, relations. Prisma generates both the client types and the migration SQL from it. Learning the schema language well means you rarely need to touch SQL, and know exactly when you must.

Prerequisites: [Setup](./01-setup.md).

## Anatomy of a model

```prisma
enum Role {
  USER
  ADMIN
}

model User {
  id           String   @id @default(uuid())
  email        String   @unique
  name         String?                              // optional (nullable)
  passwordHash String   @map("password_hash")
  role         Role     @default(USER)
  active       Boolean  @default(true)
  createdAt    DateTime @default(now()) @map("created_at")
  updatedAt    DateTime @updatedAt @map("updated_at")

  posts        Post[]                               // relation field (not a column)

  @@index([createdAt])
  @@map("users")
}
```

Reading it:

- A **model** maps to a table; **fields** map to columns (or to relations).
- Type modifiers: `String?` nullable, `String[]` list (scalar lists are supported on some databases such as PostgreSQL; relation lists are always supported).
- **Attributes** (`@`) apply to a field; **block attributes** (`@@`) apply to the model.
- `@map("snake_case")` and `@@map("table")` rename columns/tables in the database while keeping idiomatic names in the client. Decide on a naming convention early.

## Scalar types

| Prisma type | Typical JS/TS type in the client | Notes |
|-------------|----------------------------------|-------|
| `String` | `string` | Use `@db.VarChar(255)` etc. for native types |
| `Int` | `number` | 32-bit |
| `BigInt` | `bigint` | **Not JSON-serializable** by default (see below) |
| `Float` | `number` | Floating point; not for money |
| `Decimal` | `Prisma.Decimal` (decimal.js) | **Not a `number`**; use for money |
| `Boolean` | `boolean` | |
| `DateTime` | `Date` | Stored with the database's timestamp type |
| `Json` | `Prisma.JsonValue` | Untyped; validate shape yourself |
| `Bytes` | `Buffer`/`Uint8Array` | |

Gotchas:

- **`BigInt`** values are real `bigint`s. `JSON.stringify` throws on them ("Do not know how to serialize a BigInt"), so a controller returning a BigInt field fails. Convert to string/number in your response mapping.
- **`Decimal`** returns a `Prisma.Decimal` object, which serializes to a string in JSON. That's intentional (no precision loss). Don't cast it to `number` for arithmetic on money; use its methods or integer minor units (cents).
- **`Json`** fields are typed loosely. Validate the shape with a schema/DTO before writing, and narrow when reading.

### Native database types

```prisma
name    String   @db.VarChar(100)
bio     String   @db.Text
price   Decimal  @db.Decimal(10, 2)
created DateTime @db.Timestamptz(6)
```

Without `@db.*` Prisma picks a default native type per provider. Be explicit where size, precision, or timezone handling matters.

## IDs and defaults

```prisma
id String @id @default(uuid())              // UUID generated by Prisma
id String @id @default(cuid())              // collision-resistant string IDs
id Int    @id @default(autoincrement())     // auto-increment integer
id String @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid   // generated by the database
```

Other defaults: `@default(now())`, `@default(true)`, `@default("x")`, `@default(USER)` for enums. `@updatedAt` is maintained by the Prisma client on updates **made through Prisma**, not by the database, so raw SQL updates won't touch it.

Composite keys:

```prisma
model Membership {
  userId Int
  teamId Int
  @@id([userId, teamId])
}
```

## Constraints and indexes

```prisma
model Order {
  id        String   @id @default(uuid())
  userId    String
  reference String   @unique
  status    String
  createdAt DateTime @default(now())

  @@unique([userId, reference])          // composite unique
  @@index([userId, status])              // composite index (column order matters)
  @@index([createdAt(sort: Desc)])       // sorted index (where the database supports it)
}
```

- `@unique`/`@@unique` create unique constraints and enable `findUnique` on those fields.
- `@@index` creates indexes. **Index your foreign key columns** yourself: on PostgreSQL, foreign keys aren't indexed automatically ([indexing](../02-database-foundations/06-indexing-and-query-basics.md)).
- Some index features have no schema syntax (partial indexes with `WHERE`, expression indexes like `lower(email)`, `CONCURRENTLY`). Add them by editing the generated migration SQL ([migrations](./06-migrations.md)); Prisma may then report drift for things it can't model, so check what your version supports.

## Enums

```prisma
enum Status {
  DRAFT
  PUBLISHED
}
```

Maps to a database enum where supported (PostgreSQL, MySQL). Changing enum values later requires a migration, and removing a value that rows still use fails. Some teams prefer a string column plus validation for easier evolution.

## Relations (summary)

```prisma
model Post {
  id       String @id @default(uuid())
  authorId String
  author   User   @relation(fields: [authorId], references: [id], onDelete: Cascade)
}
```

`authorId` is the real column; `author` is a virtual relation field. Full coverage (one-to-one, many-to-many, referential actions, nested writes) is in [Relations](./04-relations.md).

## Soft delete, auditing, and other things Prisma doesn't model

There's no `@DeleteDateColumn` equivalent. Add a nullable `deletedAt` column and filter explicitly in queries, in a repository, or via a [client extension](./05-repositories.md). Same for audit columns beyond `createdAt`/`@updatedAt`. See [soft delete](../../08-architecture-and-patterns/04-real-world-patterns/02-soft-delete.md).

## Tooling

```bash
npx prisma format      # format and auto-complete relation fields
npx prisma validate    # check the schema without touching the database
npx prisma generate    # regenerate the client after changes
npx prisma studio      # browse data in a UI (development only)
```

`prisma format` is worth running habitually: it fills in missing back-relations and keeps files consistent. Use the VS Code Prisma extension for completion and formatting on save.

## MongoDB differences

With MongoDB the `id` is `String @id @default(auto()) @map("_id") @db.ObjectId`, relations use IDs without database-enforced foreign keys, and there are no SQL migrations (you use `prisma db push` to sync indexes/collections). Check the Prisma MongoDB docs; this section of the repository focuses on relational databases, and [Mongoose](../05-mongoose/README.md) is covered separately.

## Common mistakes

- **Forgetting `@@index` on foreign keys and filter columns.**
- **Using `Float` for money** instead of `Decimal` or integer minor units.
- **Returning `BigInt` fields directly** from controllers.
- **Casting `Decimal` to `number`** and losing precision.
- **Treating `Json` as typed** data without validation.
- **No `@map`/`@@map` convention**, ending up with mixed-case columns in the database.
- **Relying on `@updatedAt` for raw SQL changes.**
- **Hand-editing the database** and letting the schema drift from migrations.
- **Using enums for values that change often.**
- **Skipping `prisma format`**, leaving relations half-declared.

## Debugging

- "Error validating: ... missing the opposite relation field": run `prisma format` or add the back-relation on the other model.
- Type errors after editing the schema: re-run `prisma generate`.
- "Do not know how to serialize a BigInt": map BigInt fields to strings in your response.
- Money values off by tiny amounts: you're using `Float`, or converting `Decimal` to `number`.
- A unique lookup doesn't type-check: the field isn't `@id`/`@unique`/`@@unique`.

## Quick Summary

- `schema.prisma` defines models, types, constraints, indexes, and relations; the client and migrations derive from it.
- Use `@map`/`@@map` for database naming, `@db.*` for precise native types, and `@@index` for foreign keys and hot filters.
- `BigInt` isn't JSON-serializable and `Decimal` isn't a `number`; `Json` is untyped.
- `@updatedAt` is client-side; partial/expression indexes need SQL in migrations.
- Soft delete and auditing aren't built in; model them explicitly.
