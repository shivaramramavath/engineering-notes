## 1. What & Why

In production API ecosystems, error responses are just as critical as success responses. Poor error handling leads to security leaks (raw stack traces exposed to attackers), client integration headaches (every service invented its own proprietary error JSON format), and operational blind spots.

### The Problem
Historically:
1. Team A returned `{"error": "message"}`, Team B returned `{"errCode": 404, "msg": "..."}`, and Team C returned raw HTML error pages.
2. API consumers had to build dozens of different error deserializers.
3. Unhandled exceptions leaked internal database connection strings, SQL statements, and server framework versions.

### The Solution: RFC 9457 / RFC 7807 Problem Details
Spring Boot 3 natively adopts **RFC 9457** (formerly RFC 7807): "Problem Details for HTTP APIs". It introduces the standard `org.springframework.http.ProblemDetail` class with content type `application/problem+json`, defining a standard, machine-readable JSON format for errors across all services. Combined with `@RestControllerAdvice` and `ResponseEntityExceptionHandler`, Spring Boot provides a unified error handling architecture.

## 2. Core Concepts

### Mental Model & Standard RFC 9457 Payload
An RFC 9457 payload contains standard attributes alongside custom extensions:

```json
{
  "type": "https://api.example.com/errors/insufficient-funds",
  "title": "Insufficient Account Balance",
  "status": 403,
  "detail": "Account balance of $12.50 is below required withdrawal amount of $50.00",
  "instance": "/api/v1/accounts/ACC-10293/withdraw",
  "timestamp": "2026-11-24T14:32:00Z",
  "accountBalance": 12.50,
  "requiredAmount": 50.00
}
```

### Core Fields Defined by Specification
- **`type`** (`URI`): An absolute or relative URI identifying the specific problem type (defaults to `about:blank`).
- **`title`** (`String`): A short, human-readable summary of the problem type (should not change from occurrence to occurrence).
- **`status`** (`int`): The HTTP status code generated by the origin server.
- **`detail`** (`String`): A human-readable explanation specific to this occurrence of the problem.
- **`instance`** (`URI`): An absolute or relative URI identifying the specific occurrence of the problem.
- **Extension Members**: Additional custom fields attached via `.setProperty(key, value)`.

## 3. How It Works Internally

### The Exception Resolution Chain
```
              Controller throws Exception (e.g., OrderNotFoundException)
                                      │
                                      ▼
                        DispatcherServlet.doDispatch()
                                      │
                                      ▼
                      HandlerExceptionResolverComposite
                                      │
           ┌──────────────────────────┼──────────────────────────┐
           ▼                          ▼                          ▼
  ExceptionHandlerExceptionResolver  ResponseStatusExceptionResolver DefaultHandlerExceptionResolver
   (@RestControllerAdvice)           (@ResponseStatus)           (Fallback 500)
           │
           ▼
    Matches @ExceptionHandler(OrderNotFoundException.class)
           │
           ▼
    Constructs ProblemDetail Object
    Sets HTTP Status & Headers (Content-Type: application/problem+json)
           │
           ▼
    Jackson writes JSON response to client
```

### `ResponseEntityExceptionHandler` Base Class
Spring provides `ResponseEntityExceptionHandler`, an extensible base class for `@ControllerAdvice` beans. It pre-handles over 15 standard Spring MVC exceptions (including `MethodArgumentNotValidException`, `HttpRequestMethodNotSupportedException`, `HttpMediaTypeNotSupportedException`, `NoHandlerFoundException`) and automatically maps them to RFC 9457 `ProblemDetail` structures.

## 4. Syntax & Configuration

### Enabling Standard ProblemDetail via `application.yaml`
```yaml
spring:

  error:
```

## 5. Practical Examples

### Example 1: Domain Exception Hierarchy with ProblemDetail

```java
package com.example.web.error;

import org.springframework.http.HttpStatus;

import java.math.BigDecimal;
import java.net.URI;
import java.util.UUID;

public abstract class BusinessDomainException extends RuntimeException {
    private final HttpStatus status;
    private final URI type;
    private final String title;

    public BusinessDomainException(HttpStatus status, URI type, String title, String detail) {
        super(detail);
        this.status = status;
        this.type = type;
        this.title = title;
    }

    public HttpStatus getStatus() { return status; }
    public URI getType() { return type; }
    public String getTitle() { return title; }
}

public class InsufficientFundsException extends BusinessDomainException {
    private final BigDecimal currentBalance;
    private final BigDecimal requestedAmount;

    public InsufficientFundsException(UUID accountId, BigDecimal currentBalance, BigDecimal requestedAmount) {
        super(
            HttpStatus.FORBIDDEN,
            URI.create("https://api.example.com/errors/insufficient-funds"),
            "Insufficient Funds",
            String.format("Account %s has balance of %s, but required %s", accountId, currentBalance, requestedAmount)
        );
        this.currentBalance = currentBalance;
        this.requestedAmount = requestedAmount;
    }

    public BigDecimal getCurrentBalance() { return currentBalance; }
    public BigDecimal getRequestedAmount() { return requestedAmount; }
}
```

### Example 2: Enterprise Global `@RestControllerAdvice` Extending `ResponseEntityExceptionHandler`

```java
package com.example.web.error;

import jakarta.servlet.http.HttpServletRequest;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.*;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.ServletWebRequest;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

import java.net.URI;
import java.time.Instant;
import java.util.Map;
import java.util.UUID;
import java.util.stream.Collectors;

@RestControllerAdvice
public class GlobalApiExceptionHandler extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalApiExceptionHandler.class);

    /**
     * Override standard Spring validation handling to return structured ProblemDetail.
     */
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers, HttpStatusCode status, WebRequest request) {

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST,
                "Validation failed for one or more fields in the request body."
        );
        problem.setTitle("Invalid Request Payload");
        problem.setType(URI.create("https://api.example.com/errors/validation-failed"));
        problem.setInstance(URI.create(((ServletWebRequest) request).getRequest().getRequestURI()));
        problem.setProperty("timestamp", Instant.now());

        Map<String, String> fieldErrors = ex.getBindingResult().getFieldErrors().stream()
                .collect(Collectors.toMap(
                        FieldError::getField,
                        FieldError::getDefaultMessage,
                        (m1, m2) -> m1
                ));
        problem.setProperty("fieldErrors", fieldErrors);

        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
                .contentType(MediaType.APPLICATION_PROBLEM_JSON)
                .body(problem);
    }

    /**
     * Handle domain-specific business exceptions.
     */
    @ExceptionHandler(BusinessDomainException.class)
    public ResponseEntity<ProblemDetail> handleBusinessException(BusinessDomainException ex, HttpServletRequest request) {
        log.warn("Domain exception encountered: {} - {}", ex.getTitle(), ex.getMessage());

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(ex.getStatus(), ex.getMessage());
        problem.setTitle(ex.getTitle());
        problem.setType(ex.getType());
        problem.setInstance(URI.create(request.getRequestURI()));
        problem.setProperty("timestamp", Instant.now());

        if (ex instanceof InsufficientFundsException ife) {
            problem.setProperty("currentBalance", ife.getCurrentBalance());
            problem.setProperty("requestedAmount", ife.getRequestedAmount());
        }

        return ResponseEntity.status(ex.getStatus())
                .contentType(MediaType.APPLICATION_PROBLEM_JSON)
                .body(problem);
    }

    /**
     * Catch-all fallback for unexpected runtime exceptions (prevents leaking internal details).
     */
    @ExceptionHandler(Throwable.class)
    public ResponseEntity<ProblemDetail> handleUnexpectedException(Throwable ex, HttpServletRequest request) {
        String incidentId = UUID.randomUUID().toString();
        log.error("Unhandled system error [incidentId={}]: {}", incidentId, ex.getMessage(), ex);

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.INTERNAL_SERVER_ERROR,
                "An unexpected internal error occurred. Please reference the incident ID when contacting support."
        );
        problem.setTitle("Internal Server Error");
        problem.setType(URI.create("https://api.example.com/errors/internal-server-error"));
        problem.setInstance(URI.create(request.getRequestURI()));
        problem.setProperty("timestamp", Instant.now());
        problem.setProperty("incidentId", incidentId);

        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .contentType(MediaType.APPLICATION_PROBLEM_JSON)
                .body(problem);
    }
}
```

### Example 3: Edge Case — Handling Errors Outside DispatcherServlet (Filter Chain Errors)

When an exception occurs before reaching `DispatcherServlet` (e.g., inside a custom `ServletFilter` or Spring Security filter), standard `@RestControllerAdvice` cannot catch it. A dedicated `AuthenticationEntryPoint` or filter-level error bridge is required.

```java
package com.example.web.error;

import com.fasterxml.jackson.databind.ObjectMapper;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ProblemDetail;
import org.springframework.stereotype.Component;

import java.io.IOException;
import java.net.URI;
import java.time.Instant;

@Component
public class FilterLevelProblemDetailWriter {

    private final ObjectMapper objectMapper;

    public FilterLevelProblemDetailWriter(ObjectMapper objectMapper) {
        this.objectMapper = objectMapper;
    }

    public void writeProblem(HttpServletRequest request, HttpServletResponse response, HttpStatus status, String message) throws IOException {
        response.setStatus(status.value());
        response.setContentType(MediaType.APPLICATION_PROBLEM_JSON_VALUE);

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(status, message);
        problem.setTitle(status.getReasonPhrase());
        problem.setInstance(URI.create(request.getRequestURI()));
        problem.setProperty("timestamp", Instant.now());

        objectMapper.writeValue(response.getOutputStream(), problem);
    }
}
```

### Example 4: Anti-Pattern vs Production Fix

#### Anti-Pattern: Returning Raw Strings or Generic Maps with Leaked Stack Traces
```java
// ANTI-PATTERN: Exposing raw exception details and unstandardized structure
@ExceptionHandler(Exception.class)
public ResponseEntity<Map<String, Object>> handleBad(Exception ex) {
    Map<String, Object> map = new HashMap<>();
    map.put("error", ex.getMessage());
    map.put("stackTrace", ex.getStackTrace()); // CRITICAL SECURITY VULNERABILITY!
    return ResponseEntity.status(500).body(map);
}
```

#### Production Fix: Standardized ProblemDetail with Incident Tracking
```java
// PRODUCTION FIX: Generate unique incident ID, log stack trace internally, return RFC 9457
@ExceptionHandler(Exception.class)
public ResponseEntity<ProblemDetail> handleGood(Exception ex, HttpServletRequest request) {
    String incidentId = UUID.randomUUID().toString();
    log.error("Internal failure [Incident: {}]", incidentId, ex); // Log internally

    ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR,
            "Internal system error occurred. Reference incident ID: " + incidentId
    );
    problem.setProperty("incidentId", incidentId);
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .contentType(MediaType.APPLICATION_PROBLEM_JSON)
            .body(problem);
}
```

### Example 5: High-Performance ResponseStatusException

```java
package com.example.web.controller;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;

import java.util.UUID;

@RestController
@RequestMapping("/api/v1/orders")
public class LightweightOrderController {

    @GetMapping("/{id}")
    public String getOrder(@PathVariable UUID id) {
        // Lightweight inline error: Spring Boot translates this directly into ProblemDetail!
        if (id.toString().startsWith("00000000")) {
            throw new ResponseStatusException(
                    HttpStatus.NOT_FOUND,
                    "Order " + id + " does not exist or has been permanently purged."
            );
        }
        return "Order details for: " + id;
    }
}
```

## 6. Best Practices

1. **Always Extend `ResponseEntityExceptionHandler`**: It provides out-of-the-box handling for standard framework exceptions (`MethodArgumentNotValidException`, `HttpRequestMethodNotSupportedException`, etc.), preventing inconsistent fallbacks.
2. **Never Expose Stack Traces in Production**: Configure `server.error.include-stacktrace: never` to prevent attackers from discovering library versions and internal paths.
3. **Use Incident Tracking IDs for 500 Errors**: Attach an opaque `incidentId` (UUID) to 500 error responses and log the matching stack trace internally to facilitate support correlation.
4. **Set Proper `Content-Type: application/problem+json`**: RFC 9457 requires this specific MIME type to identify problem responses.
5. **Attach Structured Metadata**: Use `problem.setProperty(...)` to return validation error maps or domain-specific figures (e.g. current balance, requested amount).

## 7. Common Mistakes & Pitfalls

| Mistake | Why It Fails | Practical Remedy |
| :--- | :--- | :--- |
| **Omitting `spring.mvc.problemdetails.enabled=true`** | Default Spring Boot fallbacks return legacy `{"status": 404, "error": "Not Found"}` rather than RFC 9457 format. | Enable `spring.mvc.problemdetails.enabled=true` in `application.yaml`. |
| **Returning Raw Exceptions in Response Body** | Leaks internal class names, database connection URLs, and framework version metadata. | Map all exceptions to clean `ProblemDetail` instances. |
| **Forgetting Content-Type Header** | Returning `ProblemDetail` with default `application/json` violates RFC 9457 requirements. | Explicitly specify `MediaType.APPLICATION_PROBLEM_JSON` or let `ResponseEntityExceptionHandler` set it. |
| **Missing Catch-All (`Throwable.class`) Handler** | Unhandled exceptions fall through to Tomcat's default error page, emitting raw HTML 500 errors. | Register a `@ExceptionHandler(Throwable.class)` handler in `@RestControllerAdvice`. |
| **Duplicate `@ExceptionHandler` Declarations** | Defining multiple handlers for the same exception type causes nondeterministic resolution and startup warnings. | Organize exception inheritance hierarchies cleanly. |
| **Not Handling Filter-Level Exceptions** | Exceptions thrown by security filters bypass `@RestControllerAdvice`, returning unstyled error pages. | Implement custom `AuthenticationEntryPoint` using `ProblemDetail`. |

## 8. Performance & Security Considerations

### Stack Trace Generation Overhead
In high-throughput microservices, constructing exceptions (`new RuntimeException()`) incurs JVM overhead because the runtime fills in the stack trace (`fillInStackTrace()`). For business-logic rejections that occur frequently (e.g., validation or rate limits), consider overriding `fillInStackTrace()` to return `this` or returning `Optional`/`Result` types.

### Information Disclosure (CWE-209)
Detailed technical error messages (e.g., `PSQLException: relation "users" does not exist`) must never appear in `ProblemDetail.detail`. Always translate low-level persistence exceptions into generalized user-facing explanations.

## 9. Comparison: Legacy Custom Error DTO vs RFC 9457 ProblemDetail

| Aspect | Custom Proprietary Error DTO | RFC 9457 `ProblemDetail` |
| :--- | :--- | :--- |
| **Standardization** | Proprietary per team / company | IETF RFC 9457 (RFC 7807) Internet Standard |
| **MIME Type** | `application/json` | `application/problem+json` |
| **Client Ecosystem** | Requires custom client deserializers | Supported natively by modern API gateways, Swagger/OpenAPI |
| **Spring Framework Integration** | Requires manual serialization | Native framework support since Spring Boot 3.0 |
| **Extensibility** | Manual POJO fields | Built-in `.setProperty(key, value)` extension map |

## 10. Interview Questions & Deep Dives

<details>
<summary><strong>Q1: What is the difference between RFC 7807 and RFC 9457?</strong></summary>

**Answer:**
RFC 9457 (published in 2023) is the official obsoleting successor to RFC 7807 (published in 2016). It clarifies guidance on extending problem details, provides recommendations on distinguishing between transient vs permanent errors, specifies registry mechanisms for standard problem types, and maintains full backward compatibility with the core JSON schema defined in RFC 7807.
</details>

<details>
<summary><strong>Q2: Why should your `@RestControllerAdvice` extend `ResponseEntityExceptionHandler` instead of being written from scratch?</strong></summary>

**Answer:**
`ResponseEntityExceptionHandler` provides pre-built handling for all standard Spring MVC exceptions (such as `MethodArgumentNotValidException`, `HttpRequestMethodNotSupportedException`, `HttpMediaTypeNotAcceptableException`, `MissingPathVariableException`, etc.). If you write a custom advice without extending it, you must either write individual handlers for dozens of internal framework exceptions or allow them to fall through to a catch-all 500 handler, incorrectly turning 400-level client errors into 500 internal server errors.
</details>

<details>
<summary><strong>Q3: How does Spring Boot 3 enable RFC 9457 Problem Details by default?</strong></summary>

**Answer:**
Setting `spring.mvc.problemdetails.enabled=true` activates `ProblemDetailsErrorHandlingAutoConfiguration`. This auto-registers a default `ResponseEntityExceptionHandler` if no custom advice exists and instructs Spring's error controllers to format all standard error responses as `application/problem+json`.
</details>

<details>
<summary><strong>Q4: How does `ResponseStatusException` relate to `ProblemDetail`?</strong></summary>

**Answer:**
`ResponseStatusException` implements the `ErrorResponse` interface in Spring 6+. It encapsulates an HTTP status, headers, and an internal `ProblemDetail` instance. Throwing a `ResponseStatusException` allows developers to emit structured problem details directly from controllers without defining dedicated exception classes or advice methods.
</details>

<details>
<summary><strong>Q5: What is the purpose of the `instance` field in an RFC 9457 response?</strong></summary>

**Answer:**
The `instance` URI identifies the specific occurrence of the problem. In web APIs, it typically contains the exact request URI path (e.g. `/api/v1/orders/ORD-9912`) where the failure took place, allowing clients and log aggregation systems to trace which specific resource endpoint triggered the error.
</details>

<details>
<summary><strong>Q6: How do you attach custom properties to a `ProblemDetail` instance?</strong></summary>

**Answer:**
By calling `problemDetail.setProperty("propertyName", value)`. During serialization, Jackson flattens these custom properties into top-level JSON fields alongside the standard `type`, `title`, and `status` attributes.
</details>

<details>
<summary><strong>Q7: Can a `@ControllerAdvice` target specific controllers or packages?</strong></summary>

**Answer:**
Yes. `@RestControllerAdvice` attributes allow fine-grained targeting:
- `basePackages = "com.example.api.v1"`
- `assignableTypes = {OrderController.class, PaymentController.class}`
- `annotations = RestController.class`
</details>

<details>
<summary><strong>Q8: What happens if an exception is thrown inside an `@ExceptionHandler` method?</strong></summary>

**Answer:**
If an exception occurs within an `@ExceptionHandler` method, the exception resolution chain for that handler fails, and the exception bubbles up to the container's standard fallback mechanism (e.g., Tomcat's standard `/error` dispatch), usually resulting in a generic 500 Internal Server Error.
</details>

```java
// Solution:
```

```java
protected ResponseEntity<Object> handleMethodArgumentNotValid(
        MethodArgumentNotValidException ex, HttpHeaders headers, HttpStatusCode status, WebRequest request) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed");
    List<Map<String, String>> violations = ex.getBindingResult().getFieldErrors().stream()

}
```
