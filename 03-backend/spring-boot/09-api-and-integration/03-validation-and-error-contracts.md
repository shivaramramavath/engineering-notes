## 1. What & Why

### The Problem
Before standardization, every engineering team invented custom error response formats. Some returned `{ "error": "Invalid input" }`, others returned `{ "code": 400, "message": "...", "errors": [] }`, and some returned unstructured plain text or stack traces. When microservices and client applications consumed dozens of internal and external APIs, handling heterogeneous error representations resulted in fragile parsing logic, poor user experience, and obscured operational diagnostics.

### The Evolution
The Internet Engineering Task Force (IETF) published RFC 7807 (and the updated RFC 9457) defining "Problem Details for HTTP APIs" to establish a uniform media type (`application/problem+json`). Spring Framework 6 and Spring Boot 3 embraced this standard natively by introducing `org.springframework.http.ProblemDetail` and the `@ControllerAdvice` base class `ResponseEntityExceptionHandler`.

### Relevance in Modern Engineering
In cloud-native, multi-tier platforms, standardized error contracts are non-negotiable. Spring Boot's native `ProblemDetail` support provides machine-readable error metadata, distributed trace correlation IDs, timestamping, and field-level validation breakdowns out of the box without requiring third-party error handling libraries.

## 2. Core Concepts

- **RFC 7807 Specification**: A standardized specification for HTTP error payloads with five standard attributes:
  - `type` (URI): An absolute or relative URI reference identifying the problem type.
  - `title` (String): A short, human-readable summary of the problem type.
  - `status` (Integer): The HTTP status code generated by the origin server.
  - `detail` (String): A human-readable explanation specific to this occurrence of the problem.
  - `instance` (URI): A URI reference identifying the specific occurrence of the problem.
- **ProblemDetail Class**: The core Spring representation (`org.springframework.http.ProblemDetail`) encapsulating RFC 7807 fields, with extensible dynamic properties via `setProperty(String, Object)`.
- **ResponseEntityExceptionHandler**: An extensible base class for `@ControllerAdvice` beans that handles all standard Spring MVC exceptions (e.g., `MethodArgumentNotValidException`, `HttpRequestMethodNotSupportedException`) and converts them into `ProblemDetail` structures.
- **Jakarta Bean Validation**: Declarative input validation via annotations (`@NotNull`, `@Size`, `@Pattern`, `@Positive`) processed by Hibernate Validator.
- **spring.mvc.problemdetails.enabled**: Application property that instructs Spring MVC to enable RFC 7807 compliant error responses by default for built-in web exceptions.

## 3. How It Works Internally

```
+-----------------------------------------------------------------------------------+
|                        Spring MVC Exception & ProblemDetail Flow                  |
|                                                                                   |
| 1. HTTP Request Received                                                          |
|    POST /api/v1/accounts (Payload violates @Valid constraints)                    |
|                   |                                                               |
|                   v                                                               |
| 2. Controller Argument Resolution & Validation                                    |
|    +-----------------------------+                                                |
|    | Validator inspects DTO      | ---> Fails: Throws MethodArgumentNotValidException|
|    +-----------------------------+                                                |
|                   |                                                               |
|                   v                                                               |
| 3. DispatcherServlet Exception Interception                                       |
|    +-----------------------------+                                                |
|    | HandlerExceptionResolver    | ---> Delegates to @RestControllerAdvice        |
|    +-----------------------------+                                                |
|                   |                                                               |
|                   v                                                               |
| 4. GlobalExceptionHandler (extends ResponseEntityExceptionHandler)                |
|    +-----------------------------+                                                |
|    | handleMethodArgumentNotValid| ---> Extracts BindingResult FieldErrors        |
|    +-----------------------------+                                                |
|                   |                                                               |
|                   v                                                               |
| 5. ProblemDetail Construction                                                     |
|    ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed")  |
|    .setProperty("invalidParams", List.of(...))                                    |
|    .setProperty("traceId", Tracer.currentTraceId())                               |
|                   |                                                               |
|                   v                                                               |
| 6. HTTP Response: 400 Bad Request                                                 |
|    Content-Type: application/problem+json                                         |
+-----------------------------------------------------------------------------------+
```

When an exception occurs during request processing, Spring's `DispatcherServlet` routes the error through the registered `HandlerExceptionResolverComposite`. This invokes the `@RestControllerAdvice` bean extending `ResponseEntityExceptionHandler`. The method overrides extract validation error details from `MethodArgumentNotValidException`, construct an RFC 7807 compliant `ProblemDetail` object, inject additional contextual metadata (like timestamps and trace IDs), and serialize the response as `application/problem+json`.

## 5. Practical Examples

### Example 1: Domain Record with Jakarta Validation Constraints
```java
package com.example.platform.dto;

import jakarta.validation.constraints.*;
import java.math.BigDecimal;

public record CreateAccountRequest(
        @NotBlank(message = "Account holder name is required")
        @Size(min = 2, max = 100, message = "Name must be between 2 and 100 characters")
        String accountHolderName,

        @NotBlank(message = "Email address is required")
        @Email(message = "Invalid email format")
        String email,

        @NotNull(message = "Initial deposit is required")
        @DecimalMin(value = "25.00", message = "Initial deposit must be at least $25.00")
        BigDecimal initialDeposit
) {}
```

### Example 2: Enterprise Global Exception Handler Extending ResponseEntityExceptionHandler
```java
package com.example.platform.exception;

import io.micrometer.tracing.Tracer;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.ServletWebRequest;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

import java.net.URI;
import java.time.Instant;
import java.util.List;
import java.util.Map;

@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    private final Tracer tracer;

    public GlobalExceptionHandler(Tracer tracer) {
        this.tracer = tracer;
    }

    public record ValidationErrorDetail(String field, Object rejectedValue, String reason) {}

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex,
            HttpHeaders headers,
            HttpStatusCode status,
            WebRequest request) {

        List<ValidationErrorDetail> validationErrors = ex.getBindingResult()
                .getAllErrors()
                .stream()
                .filter(error -> error instanceof FieldError)
                .map(error -> (FieldError) error)
                .map(fieldError -> new ValidationErrorDetail(
                        fieldError.getField(),
                        fieldError.getRejectedValue(),
                        fieldError.getDefaultMessage()))
                .toList();

        ProblemDetail problemDetail = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, "The request payload failed input validation constraints.");
        
        problemDetail.setType(URI.create("https://api.example.com/errors/invalid-request-payload"));
        problemDetail.setTitle("Input Validation Error");
        problemDetail.setInstance(URI.create(((ServletWebRequest) request).getRequest().getRequestURI()));
        
        // Custom metadata extensions
        problemDetail.setProperty("timestamp", Instant.now());
        problemDetail.setProperty("invalidParameters", validationErrors);
        
        if (tracer.currentSpan() != null) {
            problemDetail.setProperty("traceId", tracer.currentSpan().context().traceId());
        }

        return handleExceptionInternal(ex, problemDetail, headers, status, request);
    }
}
```

### Example 3: Custom Business Exception Handled as RFC 7807 ProblemDetail
```java
package com.example.platform.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.WebRequest;

import java.net.URI;
import java.time.Instant;

public class InsufficientFundsException extends RuntimeException {
    private final String accountId;
    private final double deficit;

    public InsufficientFundsException(String accountId, double deficit) {
        super(String.format("Account %s lacks sufficient funds: deficit of $%.2f", accountId, deficit));
        this.accountId = accountId;
        this.deficit = deficit;
    }

    public String getAccountId() { return accountId; }
    public double getDeficit() { return deficit; }
}

@RestControllerAdvice
class BusinessRuleExceptionHandler {

    @ExceptionHandler(InsufficientFundsException.class)
    public ProblemDetail handleInsufficientFunds(InsufficientFundsException ex, WebRequest request) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, ex.getMessage());
        problem.setType(URI.create("https://api.example.com/errors/insufficient-funds"));
        problem.setTitle("Transaction Declined");
        problem.setProperty("accountId", ex.getAccountId());
        problem.setProperty("deficitAmount", ex.getDeficit());
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }
}
```

```java
// ANTI-PATTERN: Exposing database stack traces and internal class names directly in the error response
// @ExceptionHandler(Exception.class)
// public ResponseEntity<String> handleAll(Exception ex) {
//     return ResponseEntity.status(500).body(ex.getClass().getName() + ": " + ex.getMessage());

// FIX: Sanitize internal server errors, log the root cause, and return a sanitized RFC 7807 response
package com.example.platform.exception;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.net.URI;
import java.time.Instant;
import java.util.UUID;

@RestControllerAdvice
public class FallbackExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(FallbackExceptionHandler.class);

    @ExceptionHandler(Exception.class)
    public ProblemDetail handleUnhandledExceptions(Exception ex) {
        String incidentRef = UUID.randomUUID().toString();
        log.error("Unhandled platform exception. Incident Reference: {}", incidentRef, ex);

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.INTERNAL_SERVER_ERROR,
                "An unexpected internal error occurred. Please contact support referencing the incident ID.");
        
        problem.setType(URI.create("https://api.example.com/errors/internal-server-error"));
        problem.setTitle("Internal Server Error");
        problem.setProperty("incidentId", incidentRef);
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }
}
```

### Example 5: High-Performance Custom Cross-Field Validator
```java
package com.example.platform.validation;

import jakarta.validation.Constraint;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import jakarta.validation.Payload;

import java.lang.annotation.*;
import java.time.LocalDate;

@Target({ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = ValidDateRangeValidator.class)
@Documented
public @interface ValidDateRange {
    String message() default "Start date must precede or equal end date";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

record DateRangeRequest(LocalDate startDate, LocalDate endDate) {}

class ValidDateRangeValidator implements ConstraintValidator<ValidDateRange, DateRangeRequest> {

    @Override
    public boolean isValid(DateRangeRequest request, ConstraintValidatorContext context) {
        if (request == null || request.startDate() == null || request.endDate() == null) {
            return true; // Defer to @NotNull for null handling
        }
        return !request.startDate().isAfter(request.endDate());
    }
}
```

## 6. Best Practices

1. **Extend `ResponseEntityExceptionHandler`**: Always extend this base class to inherit comprehensive handling of all standard HTTP error conditions (404, 405, 415, 400).
2. **Never Return Raw Exception Messages in 500 Responses**: Prevent internal implementation details (SQL queries, class names, internal hosts) from leaking to external clients.
3. **Always Include Distributed Trace Identifiers**: Inject OpenTelemetry or Micrometer `traceId` and `spanId` into `ProblemDetail` custom properties for rapid triage.
4. **Use URI References for `type`**: Provide resolvable URLs or consistent URNs (e.g., `https://api.example.com/errors/invalid-token`) explaining remedies for each error condition.
5. **Differentiate 400 vs 422**: Use 400 Bad Request for syntactic or malformed payloads, and 422 Unprocessable Content for semantic business rule violations.

## 7. Common Mistakes & Pitfalls

| Mistake | Why It Fails | Practical Remedy |
|---|---|---|
| Omitting `@Valid` on controller `@RequestBody` | Controller executes without triggering validation constraints | Ensure `@Valid` or `@Validated` precedes every request body parameter. |
| Catching generic `Throwable` or `Exception` and swallowing trace | Obscures critical server bugs and makes production incidents untraceable | Log the exception with full stack trace at ERROR level and generate a unique tracking ID. |
| Overwriting standard response headers when returning `ProblemDetail` | Missing `Content-Type: application/problem+json` header | Use Spring's built-in `ProblemDetail` serialization or return `ResponseEntity.status(...).body(problem)`. |
| Exposing database column names in validation errors | Violates OWASP information exposure guidelines | Customize DTO validation messages using generic domain terms rather than SQL field names. |
| Returning HTTP 200 with an `{ "error": true }` body | Violates HTTP protocol semantics and breaks caching/proxy layers | Return appropriate 4xx/5xx status codes matching HTTP standards. |
| Forgetting to validate collections (`List<@Valid ItemDto>`) | Elements inside collections are skipped by the validator | Annotate collection parameters with `@Valid` on both container and element levels. |

## 8. Performance & Security Notes

- **Validator Overhead**: Bean Validation uses reflection and metadata inspection. Hibernate Validator caches metadata after initial compilation, ensuring negligible per-request overhead.
- **OWASP Information Disclosure (A05:2021)**: Standardized errors must never reveal server versions, internal database structures, or framework versions.
- **Memory Footprint**: `ProblemDetail` instances are short-lived transient objects easily collected by the JVM Young Generation garbage collector.

## 9. Comparison / When to Use What

| Error Representation | RFC 7807 ProblemDetail | Legacy Custom Error DTO | Spring Default ErrorAttributes |
|---|---|---|---|
| **Standardization** | Official IETF RFC 7807 / 9457 | Proprietary per team/company | Spring Boot default JSON format |
| **Media Type** | `application/problem+json` | `application/json` | `application/json` |
| **Tooling Support** | Broad industry tooling (OpenAPI, Postman) | Requires custom client parsing | Proprietary to Spring Boot |
| **Extensibility** | Key-value properties via `setProperty()` | Custom POJO fields | Limited to `ErrorAttributes` map |

## 10. Interview Questions

<details>
<summary>1. What is RFC 7807 and why did Spring Boot 3 adopt it natively?</summary>
RFC 7807 defines "Problem Details for HTTP APIs", establishing a standard format and media type (`application/problem+json`) for conveying machine-readable errors. Spring Boot 3 adopted it natively to provide a standardized, consistent error representation across the entire ecosystem without requiring custom DTOs.
</details>

<details>
<summary>2. What are the core standard fields in an RFC 7807 ProblemDetail object?</summary>
The five standard fields are: `type` (URI), `title` (short summary), `status` (HTTP status code), `detail` (specific explanation), and `instance` (URI identifying the specific request/resource).
</details>

<details>
<summary>3. Why should custom `@ControllerAdvice` classes extend `ResponseEntityExceptionHandler`?</summary>
`ResponseEntityExceptionHandler` provides centralized, battle-tested exception handling methods for all standard Spring MVC exceptions (such as `MethodArgumentNotValidException`, `NoHandlerFoundException`, `HttpRequestMethodNotSupportedException`). Extending it prevents developers from re-implementing dozens of boilerplate handlers.
</details>

<details>
<summary>4. How do you append custom properties to a ProblemDetail response?</summary>
You use the `problemDetail.setProperty(String key, Object value)` method. Spring's Jackson serializer automatically flattens these properties into the root JSON object of the response.
</details>

<details>
<summary>5. What is the difference between `@Valid` and `@Validated` in Spring Boot?</summary>
`@Valid` is the standard Jakarta EE annotation used on method arguments and fields to trigger Bean Validation. `@Validated` is a Spring-specific annotation that can be placed on class levels to enable method-level validation on Spring Beans, and supports validation groups.
</details>

<details>
<summary>6. How can you globally enable RFC 7807 problem details in Spring Boot without writing custom code?</summary>
Set `spring.mvc.problemdetails.enabled=true` in `application.properties`. This instructs Spring MVC's default exception resolvers to produce `application/problem+json` responses.
</details>

<details>
<summary>7. How do you capture and return field-level validation errors using ProblemDetail?</summary>
In a `@RestControllerAdvice` overriding `handleMethodArgumentNotValid`, inspect `ex.getBindingResult().getFieldErrors()`, map them to a list of error records (field, rejectedValue, message), and attach them to the problem detail using `problemDetail.setProperty("invalidParams", errorList)`.
</details>

<details>
<summary>8. How should sensitive exceptions (like DataAccessException) be handled in production?</summary>
They must be intercepted by a catch-all `@ExceptionHandler(Exception.class)`, assigned a unique correlation/incident ID, logged internally with full stack traces, and returned to the client as an opaque HTTP 500 `ProblemDetail` containing only the incident ID.
</details>
