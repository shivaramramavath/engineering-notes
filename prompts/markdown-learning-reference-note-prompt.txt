WRITING RULES
- Write like an experienced developer explaining to another developer. Open with
  a concise what-and-why. Natural flow: what -> why -> how -> when -> practical
  usage; start simple, then go deeper.
- Teach the concepts developers actually need; prefer practical code to long
  theory; explain code only where behaviour is not obvious; correct common
  misconceptions; include what breaks and how to debug it.
- No filler, no repetition across sections, no generic textbook tone. Do not
  invent APIs, behaviour, versions, links or features. No copied text from docs,
  books or blogs (one short snippet with a link at most).
- Tables only when they clarify; ASCII/mermaid diagrams only when they explain a
  flow, lifecycle, memory layout or architecture. Include performance,
  security, internals or production notes ONLY when relevant to the topic.
  Version-specific behaviour only when it matters (tag "Since vX", say what to do
  on older versions).
 
STRUCTURE (supersedes the old "no fixed template" rule)
Use the track's concept template as the skeleton (title, one-line summary

STYLE variants:
- problem-first pattern/principle: use the repo's 17-section problem-first
  format (problem -> why it exists -> what it is -> problem without it with a

- algorithm (ML/DSA): intuition, algorithm card, diagrams, math, from-scratch

- cheatsheet/interview: dense, scannable, no tutorial prose; verified answers.
Length: as long as the topic needs (usually 300-700 lines); split into two notes
if it would exceed ~900 lines or covers unrelated concepts.
